# BOOK-006 门店能力：当前边界与实施清单

当前代码的 `BookingCreateToolInput`、Gateway 创建预约和 Java 的
`BookingCreateRequest` 没有 `storeId`。旧主服务 `Organization` 有名称及地址，
`Course`、`Appointment` 关联 `organization_id`；仓库中没有明确的机构与门店
父子关系或课程、教练与门店的授权关系。组织地址不能自动视为门店身份；不能用
`organization_id` 冒充用户选择的门店，也不能把新增但未同步的空表视为权威数据。

`bash scripts/task_eval_cross_service_booking.sh --booking-capabilities-trial "$PWD/var/task-eval/booking-capabilities-new.json"`
会先启动一次性的本地服务和数据库，再在已验证的
一次性评测 MySQL 内读取少量指定表/列名，结果始终将 BOOK-006 和 BOOK-009 标记
为 `UNKNOWN`。该命令的退出码 3 表示完成了有限的结构观察，并不表示业务能力或
案例通过；存在同名字段也不证明其中数据真实、归属正确或服务实际使用这些字段。
观察对象只包括固定名称，并非对所有潜在模式的穷举。输出路径必须是不存在的绝对
路径；驱动使用独占创建并限制为当前用户读写。评测启动器提供运行 ID、容器 ID、
本机 Docker socket 及新建临时库；不得指向共享业务数据库。结构观察不检查生产
业务数据，不构成产品兼容或安全审计。

落地完整门店选择之前，应先建立以下明确的业务合同及数据来源：

1. **权威主数据**：定义门店稳定 ID、所属机构、启停状态及数据维护责任；核实
   现有组织、课程和教练数据与实体门店的映射。任何新增关系表须由受控导入或有
   鉴权的管理流程维护，不得由模型或评测程序自由创建生产关系。
2. **关系与历史数据迁移**：明确机构—门店、门店—课程、门店—教练的有效期及
   多对多规则；制定可回滚迁移、历史预约门店回填和无法唯一确定时的处理方式。
   对旧请求采用明确的兼容策略，不能在缺门店时静默选一个候选。
3. **预约协议和确认**：工具输入、Gateway、Booking DTO、确认展示、加密 payload
   及规范化签名必须使用相同的门店 ID。重试、重放和参数被篡改时应验证原签名与
   请求一致；门店必须经过服务端机构/课程/教练关系检查并在事务内记录。
4. **读取和生命周期**：预约详情、操作查询、改约/取消及通知应明确返回或保留
   原门店；定义门店关闭、课程迁移、确认后关系变化和跨门店改约时的语义。
5. **隔离验收**：准备至少两个同机构门店、另一个机构的门店、各自课程/教练和
   用户，验证歧义时追问、明确指定时确认展示与实际落库一致，以及跨机构和错误
   课程/教练关系拒绝。包含并发变化、签名换绑、重试幂等、回滚和观察窗口内
   未确认写入的独立审计；分别记录真实服务和业务数据来源。
6. **案例冻结与复核**：根据最终业务合同更新版本化案例与夹具，审核预计断言、
   维护隔离的测试集，重新运行真实 Agent 和业务服务，不能沿用旧草案的 PASS。

BOOK-009 的课程容量是另一个业务能力：现有预约实现按教练和学员时间冲突及合同
课时判断，不能把合同剩余课时当团课剩余名额。它还需要权威班次/容量、按班次的
事务锁及占座和释放规则、并发超卖测试、取消/改约后的库存处理；这些不由本门店
清单隐含实现。
