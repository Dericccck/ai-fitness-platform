# AI 健身平台：性能、召回、并发与续费效果实测

测试日期：2026-10-06。本文补充之前“需要真实测试或运行证据”的部分。

先说结论：已经得到真实本地检索、真实模型调用和实际 HTTP Agent 问答的数据；**没有得到真实用户续费提升证据**。真实调用不等于真实生产规模：本次使用固定合成业务资料与合成测试身份，没有访问会员的真实健康信息或批准业务写入。

## 二、测试环境和证据范围

### 2.1 实际使用了哪些组件

- 本机 Apple M1 Pro，10 核 CPU，32 GiB 内存；PyTorch 测试进程设置为 4 个 CPU 计算线程。
- 本地 BGE-M3 Embedding（1024 维）和已配置的 BGE Cross-Encoder Reranker，使用现有真实权重，不是 Mock。
- 本机 Docker PostgreSQL/pgvector，使用 SQLAlchemy 真实连接池和现有迁移。
- 完整问答还使用实际 Redis 配额、会话锁、共享模型并发租约、LangGraph Supervisor/领域子图、PostgreSQL Checkpointer、加密任务结果和用量台账。
- 实际调用当前配置的 `deepseek-v4-flash`；长上下文对比 temperature=0、输出上限160 Token、不执行工具。
- HTTP 测试通过绑定本机临时端口的 Uvicorn 服务进行，不是用健康检查响应时间代替问答性能。

本次没有启动 Java Gateway/训练/预约/客服业务服务，也没有部署阿里云。因此完整问答验证的是**不需要动态 Java 事实的健身知识问答链路**，不是预约确认、合同查询、训练发布、支付或通知投递的全业务容量测试。

### 2.2 数据如何隔离

每轮数据库测试都创建随机命名的 `fitness_evidence_<随机值>` 临时库，迁移到当前 head，再写入合成语料。测试结束关闭服务和连接，只删除该轮精确临时库，不修改真实会员数据，不执行 FLUSHDB。

HTTP 请求使用独立合成用户与会话，短期签名秘钥只存在测试进程内，不进入报告。Redis 中测试配额等短期键按现有 TTL 过期；这不是正式登录/身份提供方验收。

本轮按照 PostgreSQL 最佳实践检查了连接池与实际查询计划，使用 `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` 保留计划，没有为小数据集强行关闭顺序扫描或把索引示例中的数字当成实测。

## 三、首次检索：2.66 秒到 0.39 秒是怎么来的

### 3.1 比较的是哪一段

固定同一问题、同一数据库、同一权限、同一权重、Top-K和20候选：

1. 懒加载组：新建真实模型对象，不先预热，直接执行 `RagService.search()`。第一次请求承担权重加载和第一次推理成本。
2. 预热组：新建相同模型对象，先调用生产启动流程同样的 `warmup_local_embedding()`、`warmup_local_model()`，再执行相同搜索。
3. 两组使用交替顺序，记录首请求和预热耗时，保留全部6次结果。

| 配对 | 懒加载首请求 | 预热后首请求 | 少等多少 | 预热准备耗时 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 4.050 | 0.384 | 3.666 | 2.138 |
| 2 | 1.961 | 0.410 | 1.551 | 1.772 |
| 3 | 1.977 | 0.377 | 1.600 | 1.757 |
| 平均 | 2.663 | 0.390 | 2.272 | 1.889 |

六次检索的Top-5相同，相关文档均命中。优化不靠缓存答案、不减少权限条件、不跳过重排，主要是避免让首位用户承担本地模型初始化。

### 3.2 不能把这个数字讲错

这是同一进程中新的模型对象，不是六次从零重启操作系统或容器。模块导入、系统文件缓存可能已热，且第一组懒加载比后两组更慢，说明初始化测量本身有变异。

如果把“预热 + 首请求”都算进去，平均约2.279秒，而懒加载首请求约2.663秒；这个总时间差并未在小样本中得到稳定证明。**最可靠的收益是把成本移到就绪之前**，不是把模型加载计算消灭了。

预热的代价也需要说明：增加启动时长和内存常驻；启动探针要给足时间；自动扩缩容不能只看应用进程已启动就导入流量。预热失败或超时应拒绝 ready，而不是接受请求后才报缺模型。

当前运行配置此前未启用该开关。本轮没有擅自修改你的 `.env` 或发布云端，仅在 staging/production **示例配置**中补了：

```dotenv
AGENT_LOCAL_MODEL_WARMUP_ENABLED=true
AGENT_LOCAL_MODEL_WARMUP_TIMEOUT_SECONDS=180
```

实际部署必须同步应用配置，才能获得同类首请求收益。远程模型后端的本地预热方法是 no-op，不会让托管LLM前缀缓存必然命中。

## 四、召回：98.08% 到 100% 怎么提升的

### 4.1 评测不是提前填好答案再评分

原来的 `app.rag.evaluation_cli` 使用 fixture 中预先填写的 retrieved_ids，适合检验评分与门禁规则，不能证明真实检索模型的召回率。本轮新增的[固定测试集](../fitness-agent-service/evals/rag_runtime_benchmark.json)没有 retrieved_ids：每个ID均来自真实检索结果。

测试集包括：

- 30份可访问资料、4份禁止访问资料，共34份文档，每份一个分块。
- 16条语义表达、6条规则编号查询、4条多知识点组合问题，共26条。
- 禁止资料分别覆盖其他机构、其他用户私有资料、角色限制和已归档版本。
- relevant_ids 在检索前固定，评测后没有修改。

这是本轮自建的合成集，**没有独立领域专家标注复核，也不属于大规模真实用户查询集**。接近100%的分数可能主要来自语料很小、问题较容易，不能外推为复杂PDF/OCR和真实生产查询的100%准确率。

### 4.2 同条件消融结果

| 方案 | Recall@5 | MRR | 禁止文档命中 |
| --- | ---: | ---: | ---: |
| 向量召回Top-5 | 98.08% | 1.000 | 0 |
| 关键词召回Top-5 | 23.08% | 0.231 | 0 |
| 向量+关键词，RRF，无重排 | 98.08% | 1.000 | 0 |
| 当前混合召回+真实Reranker | 100% | 1.000 | 0 |

Recall@5 是每题相关文档命中比例的平均值，不是“用户满意率”，也不是“回答完全正确率”。MRR 看首个相关结果的位置；本轮向量检索已经把至少一个相关结果放在第一位，因此 MRR 没有提升。

本轮提升发生在 q26：“怎样安全补水，同时避免异常疼痛还继续练？”标注需要 `water` 和 `pain` 两份资料：

- 单向量Top-5有 `water`，但没有 `pain`，该题Recall为0.5。
- `pain` 在候选范围内，经过重排后进入Top-5，该题Recall为1。
- 平均增加 `0.5 / 26 = 0.01923`，也就是约1.92个百分点。

不能说这1.92个百分点都是“加入关键词召回”的贡献：该题关键词召回为空，RRF单独没有改善。本次证据主要支持 **Cross-Encoder 对组合问题的重排收益**。

### 4.3 当前还暴露了什么不足

关键词只命中了6条规则编号案例，16条中文语义题和4条组合题都没有关键词命中。当前 PostgreSQL 使用 `simple` 全文解析和完整 query 的 ILIKE，并非中文分词搜索引擎；这能解释一部分现象，但不能只凭26题断言所有中文检索都失败。

下一步可加入中文分词/关键词提取，扩充缩写、错别字、长问题、同义词、表格、OCR噪声、跨页上下文、无答案和冲突版本的独立标注集。应另建验证集/测试集，不在同一套26题上反复调参数后仍宣称泛化提升。

权限测试目前证明这4类合成禁止文档在这些搜索中没有泄漏，不等于已证明任意数据量/身份组合都绝无越权。生产ACL仍需独立安全回归。

## 五、上下文优化：输入确实减少了，秒数没有明显下降

### 5.1 有真实历史来源的基线

历史基线来自 `afb042106daffa29424e6ade5097e20c12c0061f` 中的 `RagSearchResult.as_prompt_context()`。该函数把首个命中父章节完整放进Prompt，没有目前的正文预算。脚本保存函数摘要，并精确复现这段纯渲染行为；**没有回放整个旧系统或更换成旧模型**。

当前版本先扣掉引用/标题开销，再为Top-5均匀分配正文预算，每份证据不超过1800字符，总体不超过配置预算，同时围绕命中片段截取父上下文。

固定5份合成长父章节：旧上下文23,789字符，当前9,450字符；供应商实际报告输入13,298到5,300 Token，减少7,998 Token（60.14%）。保留了本题需要的热身时间、徒手深蹲、髋铰链等事实。8份模型回答保存在报告中供复核；这不是完整生成质量评测。

### 5.2 时间、缓存、费用分别说明

真实调用交替使用旧/新上下文，4组配对。TTFT平均少0.019秒，配对均值差95% bootstrap区间约 **[-0.131, 0.287]秒**；完整返回平均少0.007秒，区间约 **[-0.144, 0.260]秒**。两者均跨0，不支持稳定提速结论。4组太少，区间也不能代表跨天或跨供应商总体性能。

输入Token减少是清晰结果；输入变少并不保证这一时段下TTFT也等比例下降，供应商排队、网络、服务端批处理、缓存和输出速度都会影响结果。本次不人为清空供应商缓存：两版本各自首次观测命中0 Token，后续三次旧上下文均命中13,056 Token、新上下文均命中5,120 Token。两边都有高命中，因此没有隔离出“缓存本身带来多少秒”的贡献，也不把首次观测强称为供应商的绝对冷缓存；**不宣称Prefix Cache/KV Cache必然带来多少秒收益**。

价格未配置，估算成本为null。因此不能把Token减少直接写成“成本降低60%”：缓存输入单价、输出Token、服务器和本地模型运行成本均会影响费用。

### 5.3 追加测试：前缀缓存现在能算出多少

收到“这些现在还不能帮我得出提升多少、下降到多少吗”的追问后，额外运行现有 `llm_performance_benchmark.py`，不是只给测试建议。仍使用真实 `deepseek-v4-flash` 和现有 ModelGateway/LangGraph 流；只发送合成热身资料，不访问会员信息，不执行工具，不修改生产代码或真实运行配置。

这轮固定100行合成健身资料、同一个两句话热身问题，temperature=0、最大输出128 Token，共6组12次真实模型调用。稳定组保持System Prompt不变；变化组每次在System Prompt最前面加入随机基准编号。第1、3、5组先稳定后变化，第2、4、6组先变化后稳定，避免所有缓存组都排在后半段。

| 配对 | 变化前缀：首个增量 | 稳定前缀：首个增量 | 变化前缀：完整返回 | 稳定前缀：完整返回 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 0.516 | 0.576 | 0.723 | 0.844 |
| 2 | 0.838 | 0.687 | 0.871 | 0.832 |
| 3 | 0.645 | 0.538 | 0.654 | 0.592 |
| 4 | 0.593 | 0.194 | 0.717 | 0.347 |
| 5 | 0.524 | 0.733 | 0.557 | 1.024 |
| 6 | 0.487 | 0.478 | 0.532 | 0.571 |
| 平均 | 0.600 | 0.534 | 0.676 | 0.702 |

可以直接计算的事实是：

- 稳定组6/6调用报告缓存命中，每次命中2048/2228个输入Token，缓存输入占比约91.92%；变化组6次命中均为0。**91.92%是输入Token缓存占比，不是延迟或费用下降比例。**
- 首个答案增量平均从0.600466秒到0.534158秒，样本平均少0.066308秒，约11.04%。配对均值差95% bootstrap区间约 **[-0.074, 0.226]秒**，跨过0；首字中位数则只有0.558399秒到0.556544秒。少量特别快或特别慢的观测对平均数影响较大，尚未证明稳定的首字提速。
- 完整返回平均从0.675792秒到0.701679秒，样本平均**增加0.025887秒，约3.83%**；以“减少”为正的配对区间约 **[-0.233, 0.178]秒**，也跨过0。没有隐藏这项负向结果，也不把它解释为已证明缓存导致变慢。

这组对照并不等于供应商提供的缓存开关实验：变化组随机编号使输入Token从稳定组2228变为2250～2256，生成答案长度也有差异（稳定组均24 Token，变化组18～31 Token）；随机内容本身、网络和供应商调度都可能影响输出与时间。报告只捕获首个 `answer.delta` 事件，没有另做浏览器渲染计时或逐条首增量空白校验。因此这里称“模型链路首个答案增量”的测量，不宣称是浏览器可见端到端TTFT。

**本轮能证明观察到缓存命中，能计算样本差值，不能证明“Prefix Cache/KV Cache使完整Agent TTFT降低11.04%”，更不能写60%。** 不直接操纵托管服务的内部KV Cache，也不保证任意请求一定命中。没有真实账单价格、独立回答质量评审或跨时段样本，不输出成本和质量提升结论。

与5.2的长父章节实验要分开：本轮是另一组固定问题/输入规模的稳定前缀对照，不能把0.600秒当成之前完整Agent的历史基线，不能拼接两个实验的最快结果组成“旧版→新版”。完整健身知识问答目前已实测约2.956秒（1并发、4次），但尚无相同环境下“旧版15秒”的回放证据。带工具Schema回合的内容缓冲规则也没有因本轮测试而改变。

## 六、SSE：直接模型流和完整Agent要分开

### 6.1 工具为空的真实模型流

当前长上下文的4次请求，收到首个有效答案平均0.643秒，完整结束平均0.931秒。如果等到结束才展示，用户比收到首个增量平均多等约0.289秒。

这说明在**允许立即公开文本**的回合，LangGraph custom事件接入SSE可以更早展示，但没有把模型完整推理的0.931秒变成0.643秒。也不能把展示提前约31%写成整个Agent系统延迟降低31%。

### 6.2 这次完整Agent为什么没有Token级首字结果

当前 `ModelGateway._stream_with_tools` 中有一个安全约束：`visible = not request.get("tools")`。只要该回合给模型提供了工具Schema，就先缓冲内容，避免把工具选择前的文本、内部协议或未经核验的成功声明提前公开。

此次健身知识问答仍携带当前意图的读工具Schema。即便模型最后没有调用工具，也没有向客户端发出 `answer.delta`。12次请求的有效答案在 `run.completed` 中交付，所以报告TTFT为null，**不是首字0秒**；用户的可见等待接近完整返回耗时。

未来若要真正改善这条路径，可以研究两阶段执行：先选择/执行必要工具，再进入没有工具Schema的最终回答流；纯静态知识问答也可以设计明确的安全直达路径。代价是可能多一次模型调用，需要比较成本、完整耗时与首字体验，并继续验证确认、敏感输出、事实引用和断线恢复。不能为了一个好看的秒数直接删除业务权限或工具安全边界。

这里每条请求实际走 Embedding→授权向量/关键词召回→RRF→Reranker，没有预填答案。计时从并发槽位获得后开始；压测调度器等待槽位的时间没有包含在单请求延迟中。吞吐用整批实际墙钟时间计算。

串行26题平均0.372秒，样本P95约0.412秒。8并发仍全部成功，但吞吐未高于4并发，延迟约翻倍；不能把“成功处理8并发”讲成“并发越高性能越好”。不同批次请求数和查询构成并非完全相同，尚不足以做严格容量曲线或最大吞吐证明。

真实向量SQL的EXPLAIN执行约0.256毫秒，小语料顺序扫描是合理计划；本次查询时间远低于整体检索约0.372秒。因此本轮更应关注本地Embedding/Cross-Encoder的CPU计算与线程竞争，而不是马上迁移Viking DB或强行给小表增加索引。这是结合计划与耗时的推断，仍需更完整的分段profile确认。

后续可验证候选数量/批大小、CPU线程数、有界推理队列、GPU或独立推理服务。每种优化都应同步比较召回和延迟，不能仅减少候选、牺牲质量后宣称“优化成功”。

## 八、续费率为什么暂时不能补一个提升数字

### 8.1 技术能力不等于业务效果

主动提醒、课时预警、个性化训练建议和经营决策可以构成实验干预，但“已实现提醒”不等于“让用户多续费”。本轮没有获得可审计的真实用户随机分组和成熟净支付结果数据，不能从单元测试、模拟用户、人工构造两组转化数、打开通知人数推导真实续费收益。

新增[聚合数据模板](../fitness-agent-service/evals/renewal_observation_template.json)和[分析工具](../fitness-agent-service/scripts/renewal_effect_check.py)。模板中的0只是“尚未提供真实观察数据”，不是声称生产续费人数为0；当前执行结果是：

```json
{"status":"DATA_INSUFFICIENT","renewal_uplift_pp":null}
```

### 8.2 推荐的可审计实验口径

1. **预先定义人群**：例如会籍在未来30天到期且满足资格的会员；在发送提醒前固化资格，不能事后只挑点击过消息的人。
2. **先分组再干预**：同一会员稳定分组，实验组新增主动方案，对照组维持标准服务；不能撤掉法定或必要安全通知。
3. **按分配组分析（ITT）**：未收到、未点击、已退订的实验组会员仍保留在该组分母，另报实际曝光/点击作为过程指标。
4. **定义净续费**：在统一观察窗口内完成的真实续费支付，并在约定退款窗口结束后排除退款/撤销；跨店、多个合同和重复支付要按用户去重。
5. **统一成熟时间**：不能把已经观察60天的对照组与只观察7天的实验组直接比较；未成熟样本暂不输出正式效果。
6. **排除污染/干扰**：同一教练可能对两组会员采用同一策略。若需要按门店或教练做集群随机化，就必须使用集群方法，不可直接套本工具的独立用户区间。
7. **检查分组与数据质量**：样本比例失衡、日志丢失、同期促销、价格调整、渠道差异和重复实验暴露都应审核。
8. **预设主要指标与停止规则**：避免每隔一小时看显著性、见到一次正结果就提前结束。另跟踪投诉、退订、退款、提醒频次、人工干预和成本。

已有稳定分组与经营效果观察能力可以复用；但还需要把实验分配、实际曝光、真实续费支付和退款成熟状态串成可审计数据链。本次**没有运行生产干预、向会员发送实验消息或凭模板自动接通真实支付事件**。

### 8.3 工具输出哪些内容，哪些不会自动承诺

工具计算两组续费率、绝对差（百分点）、相对差和95% Newcombe/Wilson区间，参考 [statsmodels 两独立比例区间文档](https://www.statsmodels.org/stable/generated/statsmodels.stats.proportion.confint_proportions_2indep.html)及其实现。

没有真实来源、事前独立用户随机化、ITT、成熟观察/退款窗口和分组比例检查声明时，只输出DESCRIPTIVE_ONLY。即使输入声明全部满足，也返回RCT_DECLARED_REQUIRES_AUDIT，不自动填写因果续费提升；程序不能核验你填的数字是否真实，仍需来源和实验审核。

实验规划辅助函数提供等样本两比例正态近似。例如**假设而非本项目实测**基线30%、希望识别35%、双侧5%显著性、80%把握度，约需每组1,377位独立有效用户。流失、集群干扰、多指标和连续观察会改变样本要求，不能把这个示例当成你已有的用户规模。

## 九、可以补到简历里的表述

### 9.1 推荐的保守写法

> 基于PostgreSQL/pgvector、BGE-M3与Cross-Encoder构建带租户/角色过滤的混合RAG链路；建立固定语义、规则编号和组合查询评测集，在34份合成文档、26条查询、Top-5条件下，相比单向量召回，Recall@5由98.08%提升至100%，4类权限禁止文档零命中。

> 将本地Embedding/Reranker预热纳入服务就绪流程；在M1 Pro 32GB、本地3组首请求对比中，将就绪后的首次RAG检索平均耗时从2.66秒降至0.39秒，同时保留引用、权限过滤与重排。明确预热增加启动准备时间，不冒充稳态或完整LLM回答提速。

> 对RAG父上下文实施锚点截取与多证据均匀预算，在固定长章节、4组真实模型配对中，输入Token由13,298降至5,300，减少60.14%；记录TTFT、缓存命中与用量，未将无显著差异的延迟结果写成提升。

> 搭建实际HTTP问答与检索并发基准，完成单实例1/2/4并发、合计12次知识问答全部成功，以及8并发RAG批次16/16成功测试；结合查询计划与延迟识别CPU推理竞争迹象，保留原始报告用于容量规划。

完整请求分布为：**合计12请求分布在1/2/4并发三档，每档4个请求；4并发档为4/4**。不要改写成4并发持续跑了12次，更不要当作长期生产成功率100%的证明。

> 为主动服务建设稳定实验分组与续费效果评估方案，定义净支付、退款成熟窗口、ITT与分组审核；当前未形成真实续费增量证据。

### 9.2 不建议现在写

- “RAG准确率达到100%”“面向真实用户召回提升XX%”，没有附合成集范围。
- “完整问答从15秒降到2秒”，本次没有这组历史证据。
- “Prefix Cache/KV Cache使端到端首字延迟降低60%”，本次没有证明。
- “所有问答支持Token级SSE”，带工具回合目前先缓冲。
- “支持8并发完整业务”“支持万人在线”，混淆检索、问答与生产容量。
- “续费率提升15%”“运营收入提高20%”，没有真实实验支付数据。

小而真实的证据比大而无法复现的数字更适合面试。面试官追问时，要能说明基线、数据规模、模型、硬件、统计口径、失败记录和代价。
