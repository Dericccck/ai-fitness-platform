# 健身 Agent Memory 统一设计与实施规划

日期：2026-10-18。本文统一整理本次关于 Memory 的讨论，合并原方案与补充说明，作为后续设计评审和实施的主要入口。当前只整理设计文档，未实施业务代码、数据库迁移或生产上线验证。

## 1. 最终设计概览

Memory 保存经过用户确认、具有跨会话价值的结构化目标、偏好和适用条件。

- 保留五类，每类支持多条独立记录。
- 模型提取用户明确表达；受控目录与 Schema 定义允许的结构；程序负责授权、校验和写入。
- 新旧比对以结构化查询与规则为主，模型处理语义歧义，向量仅作为未来可选的相关项召回。
- 新增、修改、撤销形成可审阅提案；批准后，正式记忆、候选终态、修订号、审计和通知原子提交。
- 对话与计划生成统一按身份、机构、用途、条件、有效期和相关性读取。
- 支持证据、关联引用、程序应用分别统计；引用不等于用户确认。
- 遗忘结合撤销、有效期、复核与冷却，不根据长期未引用直接判定错误或删除。

两条独立主线：

1. 写入：用户表达 → 提取 → 规范化 → 相关旧项比对 → 候选 → 用户确认 → 原子保存。
2. 使用：当前请求 → 授权与用途 → 选择有效记忆 → 上下文装配 → 生成与校验 → 最终提交 → 幂等使用统计。

## 2. 当前实现与目标设计

| 方面 | 当前实现 | 目标设计 |
|---|---|---|
| 分类 | 五种 memory_type | 保留五类，增加受控 slot 目录 |
| key | 模型自由命名，仅限制长度和字符格式 | slot 由目录限定，scope/item 身份由服务端规范化生成 |
| 提取输出 | Prompt 指导 + JSON 对象模式 + 返回后 Pydantic 校验 | Prompt 与 Schema 同源；按供应商能力使用严格 Schema，并保留本地业务校验 |
| 提取入口 | 自动候选主要在训练指导子图 | 公共入口识别各场景长期表达 |
| 新旧比较 | 自动提取只看当前消息；同键正式保存会覆盖 | 新增、重复、修改、撤销、澄清明确区分 |
| 批准 | 已有候选确认；正式保存与候选状态更新分事务 | 绑定目标版本，统一命令服务单事务提交 |
| 生命周期 | 已有纠正、撤销、到期、保留清理 | 保留并完善修订号、复核、冷却和来源重放边界 |
| 正文 | 候选已加密；正式内容为结构化 JSONB | 正式正文迁移到受控加密访问层 |
| 读取 | 训练计划已接入；普通对话可经工具查询 | ContextBuilder 按场景自动选择必要记忆 |
| 引用 | RAG evidence_ids；Memory context_sources 来源清单 | 区分注入、关联引用、程序应用，按版本幂等统计 |

不能把本设计中的新增能力说成已经上线。现有纠正、撤销和到期也不能笼统说成尚未实现。

## 3. 四种数据的关系与边界

| 数据 | 内容 | 作用 |
|---|---|---|
| 聊天消息 | 用户原文、助手回复、卡片、结果通知 | 页面历史与来源追溯 |
| 会话摘要 | 当前会话的压缩信息 | 降低上下文长度 |
| Checkpoint | Agent State、消息引用、执行进度和中断 | 恢复流程 |
| 正式 Memory | 用户确认的结构化目标、偏好、条件 | 跨会话个性化 |

完整聊天档案和稳定 source_message_id 是来源追溯的前置能力。当前运行记录、历史提交标记和 Checkpoint 不能直接视为完整聊天消息表。

正式 Memory 默认按 subject_user_id + organization_id 隔离。跨机构共享需要单独的显式产品设计，不自动开放。

合同余额、预约状态、排班和可约性由 Java 查询。一次晚上预约不能推导出长期晚上偏好；助手建议、摘要、RAG 文档和业务工具结果不能充当用户偏好的新来源。当前五类也不扩展为存储医学诊断、支付事实或凭证的通用画像库。

## 4. 五类、维度和多条目身份

| memory_type | slot_code 示例 | 基数与含义 |
|---|---|---|
| TRAINING_GOAL | goals、primary_goal | 多个目标；主目标按范围单值，主次须用户明确 |
| TRAINING_PREFERENCE | exercise_preference、intensity | 动作按对象多条；强度按场景单值 |
| EQUIPMENT_AVAILABILITY | available_equipment | 按器械、地点分别保存；喜欢不等于拥有 |
| SCHEDULE_PREFERENCE | available_windows、preferred_windows、session_duration | 可用窗口、偏爱窗口分别多项；时长按范围单值 |
| COMMUNICATION_PREFERENCE | language、verbosity、output_format | 每个维度独立，可同时为中文、简洁、列表 |

五类不是五条。正式条目身份包含主体、机构，以及以下三项：

- slot_code：受控维度。
- scope_key：适用条件的服务端规范化身份，例如地点；无条件使用非 NULL 默认值。
- item_key：集合维度中的对象身份；单值维度使用固定占位。

同一个深蹲对象从 LIKE 改为 DISLIKE，item_key 不变，值和版本变化。不同动作可以共存。时间窗口新增或替换要结合用户意图和旧项，不能只根据是否出现新 key 决定。

服务端词典负责已知动作、器械的 canonical code；未知或不确定同义关系不强行合并。时间使用明确的时区和星期约定；“上午、下午、晚上”保留标签，不能自行编造精确小时。

### 4.1 周末时间示例

| 来源 | 表达 | 结果 |
|---|---|---|
| 原记忆 | 喜欢周末上午训练 | preferred_windows：周末上午 |
| 新表达 | 周末下午也可以 | available_windows：周末下午 |

保留上午偏爱，新增下午可用。推荐可先考虑上午，再查询实际可约时间；不能把“可以”融合为同等喜好。

若旧项也是“上午有空”，则在可用窗口集合新增下午。若用户说“上午不行了，只能下午”，处理相关可用窗口的替换；“不行”不自动表示不再喜欢上午。含糊时先澄清。

## 5. Prompt、Pydantic 与 JSON Schema 怎样配合

### 5.1 当前实际机制

当前 memory_type 在 Prompt 中列出五种允许值，Pydantic 也用 Literal 限定五选一。

当前 memory_key 是普通字符串，仅校验 1—64 字符和正则 `^[a-z][a-z0-9_]{0,63}$`。没有固定语义目录，因此 training_time、available_time 等都可能通过格式校验。

当前模型请求仅使用 `response_format={"type":"json_object"}`，没有把完整 Pydantic JSON Schema 传给供应商。

`Prompt + 当前用户消息 → 模型返回 JSON 文本 → json.loads → Pydantic model_validate → 二次清洗`

Pydantic 是服务端定义和校验对象，模型返回的是文本；Python 类不会自动被模型看见。JSON 对象模式也不等于五类、key 和语义组合均已得到约束。当前还存在疑似长期表达的触发筛选，并非每个问题都调用提取模型。

### 5.2 目标机制

由 MemorySlotRegistry 统一定义 type、slot、值 Schema、单值/集合、归一规则、场景白名单和冲突规则，并从同一目录生成 Prompt 和输出 Schema。

Prompt 说明语义：“有空、可以训练”属于 available_windows；“喜欢、优先安排”属于 preferred_windows。Schema 约束字段和合法组合；服务端校验证据、授权与业务含义。

模型可以输出 type 与 slot，但两者的关系必须固定验证；服务端不接受任意新 key，也不让模型生成内部 scope_key/item_key。供应商支持严格 Schema 输出时实际传入 Schema，不支持时使用明确 Prompt、JSON 模式和本地校验，不能宣称已获得同等约束。

目标提取示例（逻辑结构，未固定为已上线契约）：

~~~json
{
  "candidates": [
    {
      "memory_type": "SCHEDULE_PREFERENCE",
      "slot_code": "available_windows",
      "value": {"days": "WEEKEND", "period": "AFTERNOON"},
      "qualifiers": {},
      "intent": "SUPPLEMENT",
      "evidence_quote": "周末下午也可以"
    }
  ]
}
~~~

用户、机构、来源消息和运行 ID 由服务端绑定。语义上仍有歧义时，不因为 JSON 合法就允许写入。

## 6. 提取与新旧比较

第一阶段只从当前用户明确表达提取原子事实与原文证据。少量近期上下文可解析“这个动作”等指代，但助手说过某件事不等于用户认可；来源无法确定就询问。

程序核对证据与原文，检查否定、引用、假设和暂时性，并按 Registry 规范化。不能把整库旧 Memory 当成新事实再提取。

第二阶段按同一主体、机构、slot、对象及可能重叠的条件查询相关旧项。比较完整命题：对象、值/极性、条件、有效时间以及本轮补充或替换意图。

| 结果 | 条件与处理 |
|---|---|
| ADD | 独立且可共存的对象/窗口；生成新增提案 |
| UPDATE | 明确修改目标；绑定 memory_id 与 expected_version |
| REVOKE | 明确不再保存/使用目标；生成或执行受控撤销命令 |
| NOOP | 内容与适用范围相同；不改正文和内容版本 |
| NEEDS_CLARIFICATION | 对象、范围、补充/替换不明确；询问后再形成提案 |

完全重复与独立新增由规则优先处理。遇到范围收窄、交集、指代或语义歧义，将用户原话、新事实、相关旧项及版本、允许操作规则交给模型提出建议。模型不得直接写库；它的自评置信度也不是覆盖授权。

向量仅可辅助召回相关旧项，不决定重复、冲突或覆盖。第一版五类低数量结构化记忆不新建向量库；以后即使引入，也保留同对象和重叠范围检查，不能因为 Top-K 漏召回就认定没有冲突。

## 7. 流程 A：表达、提取、确认与入表

~~~mermaid
flowchart TD
  A[用户原文持久化，取得消息 ID 和 run_id] --> B[Agent 完成本轮交互]
  B --> C[最终消息、完成状态、提取 Outbox 同事务提交]
  C --> D[Worker 检查来源、开关和遗忘边界]
  D --> E[模型提取原子事实与证据]
  E --> F[程序校验、规范化、查询相关旧项]
  F --> G[规则比较，必要时模型辅助]
  G --> H{结果}
  H -->|有歧义| I[请求用户澄清]
  H -->|重复| J[NOOP，可记录独立用户支持来源]
  H -->|需变更| K[候选与通知入表，展示差异和来源]
  K --> L{用户决定}
  L -->|拒绝或过期| M[结束候选，不改正式记忆]
  L -->|批准| N[鉴权、幂等、TTL、提案与目标版本校验]
  N --> O[正式记忆、候选、审计、revision、通知原子提交]
  O --> P[使旧上下文失效，通知前端]
~~~

普通自动提取默认异步，不阻断业务回答。COMPLETED 表示交互完成，不表示预约等 Java 操作必然成功。失败/取消的普通轮次不自动发布候选。

显式“请记住”可以同步准备提案，随可信完成提交后发布；管理页确认编辑直接走命令服务。明确遗忘在完成必要目标识别后走独立管理命令，不依赖普通回答或自动提取成功。

没有旧项也先生成 ADD 候选，不直接写正式表。候选显示新增/修改/撤销、原文来源、条件、修改前后及保留项，允许批准、拒绝、编辑。编辑后重新校验与绑定提案版本。组合变化一次批准、全部提交。

NOOP 的新支持来源必须确属当前用户明确断言，同一消息幂等去重；不提高内容版本，不等于新批准，也不自动续期。

## 8. 流程 B：读取、上下文装配与回答

~~~mermaid
flowchart TD
  A[当前用户请求] --> B[鉴权并确定 actor、subject、机构和 purpose]
  B --> C[读取权威 revision 与用途允许的正式记忆]
  C --> D[检查状态、有效期、条件与按场景的复核要求]
  D --> E[结合本轮明确输入选择相关记忆与必要约束]
  E --> F[构造带 ID、版本和适用条件的上下文包]
  F --> G[固定 system、Memory 数据、本轮输入]
  G --> H[模型生成回答或训练草案]
  H --> I[校验结构、引用与可确定检查的约束]
  I --> J[最终消息与使用事件 Outbox 持久化]
  J --> K[返回前端，刷新可恢复]
  J --> L[幂等汇总使用统计]
  J --> M[自动提取链路独立处理本轮新表达]
~~~

提取与读取独立。本轮输入可以直接用于本轮回答，未批准的新候选不能升级为跨会话事实。例如“今天只有二十分钟”影响今天计划，不自动改长期时长。

MemoryContextBuilder 统一授权、用途筛选、有效性、相关性和预算。构造时记录注入清单；最终引用和程序应用另行记录，不能混称“全部实际使用”。待复核信息按 slot 稳定性和用途处理，必要可用时间/器械条件不确定时先问；稳定沟通偏好不因年龄一律停用。

| 场景 | 自动读取与限制 |
|---|---|
| 本人训练计划 | 相关目标、训练偏好、器械、时间和时长；校验必要约束 |
| 普通对话 | 沟通偏好与当前问题直接相关的其他信息 |
| 健身问答 | 沟通偏好及相关的目标/条件；不推断健康事实 |
| 预约 | 时间偏好辅助建议；可约性、课时、授权继续查 Java |
| 客服 | 沟通偏好，以及解决当前问题确有必要且有权读取的条目 |
| 文档生成 | 格式、沟通偏好与主题相关条件；不自动公开私人信息 |
| 教练代学员 | Java 授权后读取学员四类训练信息；不取学员沟通偏好，表达可参考教练沟通偏好 |
| 明确查询记忆 | 本人机构范围分页展示有效记忆、条件与来源 |

system 保存固定规则、权限和输出格式。MemoryContextPacket 作为单独 user 数据上下文，或实际工具调用的 tool result；原文不升级为 system 指令。工具结果须配对 tool_call_id。训练计划严格 JSON 字段不受“简洁回答”偏好削减。

运行时装配 Memory 正文，Checkpoint 优先保留引用、版本和执行进度。恢复时重新授权并检查当前有效性；失效引用明确标记，不改写历史 Java 工具结果、不重放业务写操作。当前明确要求优先，矛盾且无法确定时澄清。

## 9. 数据结构

| 表/设施 | 职责与关键内容 |
|---|---|
| agent_memories | 归属、type/slot/scope/item、加密结构化正文、内容指纹、status/version/schema_version、有效期、确认时间、来源和保留标记 |
| agent_memory_candidates | 加密变更数组、目标及预期版本、proposal_hash/version、来源、TTL、决定与状态 |
| agent_memory_events | 操作、目标、版本、actor、结果引用和幂等审计；默认不复制正文 |
| agent_memory_profiles | 用户机构范围 revision、write_epoch、提取/个性化开关及来源删除边界 |
| agent_memory_supports | 独立用户来源消息、对应记忆版本、断言时间、证据定位、确认事件引用 |
| agent_memory_usage_events | 最终统计单元、run、记忆 ID/版本、用途、使用种类、时间和校验方式 |
| agent_memory_version_stats | 每个记忆版本的支持、关联引用、程序应用汇总；与正式内容版本分开 |
| 聊天档案、Outbox、Worker | 来源消息、可靠任务、候选/生效通知和幂等交付 |

正式记忆解密后的逻辑示例：

~~~json
{
  "id": "memory-123",
  "memory_type": "TRAINING_PREFERENCE",
  "slot_code": "exercise_preference",
  "value": {"exercise": "squat", "preference": "LIKE"},
  "qualifiers": {"location": "gym"},
  "status": "ACTIVE",
  "version": 3,
  "source_message_id": "message-456",
  "last_confirmed_at": "2026-10-18T01:00:00Z",
  "expires_at": null
}
~~~

正文逻辑上是结构化 JSON，物理上计划加密存储；查询元数据单独保留。内容指纹使用带密钥 HMAC，不以低熵普通 hash 冒充保密。身份指纹与内容指纹分开，身份密钥/规范化规则迁移需要兼容和重建唯一性，不能随正文密钥轮换制造新身份。日志不写原文和解密内容。

生命周期状态 ACTIVE、REVOKED、EXPIRED，与检索层级 NORMAL/COLD、next_review_at、user_pinned 分开。待复核和低频不是自动撤销。

## 10. 原子批准、唯一性和并发

同一主体机构内，对 ACTIVE、未脱敏的 slot + scope + item 建静态部分唯一约束。它只能排除完全相同身份，重叠范围仍由服务层处理。有效期在读取和命令中检查；不能在部分索引谓词使用 expires_at > now()。

所有正式变更遵守固定顺序：profile → candidate → 按 ID 排序的 Memory。模型、HTTP 与等待确认均在锁外进行。

批准短事务：

1. 校验身份、机构、提案 hash/version、候选状态、TTL 和 write_epoch。
2. 重读目标、校验 expected_version，检查 ADD 是否重复及相关冲突。
3. 执行 ADD/UPDATE/REVOKE/NOOP；组合提案全部成功才提交。
4. 同事务提交正式记忆、候选终态、revision、审计与通知 Outbox。
5. 提交后使缓存失效并交付通知。

同操作 ID 相同请求返回原结果，换 payload 则拒绝。两个版本 3 的修改，首个成功为 4，另一个 STALE/409 重确认。不同独立偏好可共存；整库 revision 变化不能直接误伤无关提案。相同新增收敛为一条。

## 11. 证据、引用与使用计数

| 关系 | 说明 |
|---|---|
| 用户支持证据 | 这条个人信息来自哪条明确用户表达 |
| RAG 知识引用 | 训练安排的知识依据来自哪段文档 |
| Memory 使用关联 | 本份回答/计划关联了哪些个人条件 |

三者分开。当前 evidence_ids 校验 RAG citation_id；context_sources 是 Memory 来源清单，不是逐条采用证明。目标新增 used_memory_refs，包含 memory_id 与 version，不能用私人偏好代替动作的知识证据。

| 字段 | 含义 |
|---|---|
| support_count | 独立且校验通过的用户支持消息数 |
| last_user_asserted_at | 最近用户明确表达时间，采用来源时间 |
| last_confirmed_at | 当前版本最近明确批准/复核时间，只由确认命令更新 |
| injected_count / last_injected_at | 注入实际模型请求的观测，可暂只保留指标 |
| referenced_count / last_referenced_at | 已提交最终结果的声明关联次数和最近时间 |
| applied_count / last_applied_at | 确定性校验流程采用结构化约束的次数和时间 |

检索、注入、引用、程序应用、用户确认是不同事件。助手复述、摘要、RAG 或模型自己的引用不增加用户支持；用户重复表达也不等于事实一定真实或仍有效。

服务端给出本次授权注入清单，再核对模型返回的 used_memory_refs：范围、版本、用途和有效性都必须合法。仅通过白名单校验不能证明内部因果采用；器械/时长等可另由确定性校验器记录 APPLIED。普通聊天关联放元数据，不要求正文每次暴露偏好。

最终结果与使用 Outbox 同事务提交；后台插入新使用事件成功才加一。统计单元为稳定的最终回答或计划版本，同一记忆多处关联默认一次。重试、模型修复、分片、Outbox 重投、历史刷新不重复加数；迟到时间用 MAX，旧版本事件不记到新版本。

失败/取消且未提交的临时结果不计成功引用。已持久化但推送丢失的结果可恢复，计为已提交关联使用，不宣称用户看过。管理展示和查询记忆不冒充任务个性化引用。

使用汇总放独立表，引用不会增加正式内容 version。已删除的条目不能被迟到统计重建。

## 12. 复核、冷却、撤销与遗忘

| 情况 | 处理 |
|---|---|
| 用户主动遗忘 | 立即撤销并失效派生上下文，不受使用次数保护 |
| 显式有效期到期 | 停止使用；高频引用不能续期 |
| 时间、器械、阶段目标久未确认 | 按 slot/用途标记待复核，需要依赖时询问 |
| 低风险偏好长期未用 | 降低普通上下文优先级，可进入 COLD |
| 固定保留、必要排除条件与关键约束 | 不因低频自动移除，仍服从有效期、遗忘和复核 |

COLD 可在管理页和明确相关查询中找到，核对有效性后仍可使用；不是 REVOKED，更不是物理删除。沟通偏好缺少正文引用 ID 不代表无价值；用户长期没来不代表器械条件错误；频繁引用旧时间也不代表用户持续确认。

决策顺序：权限/撤销/到期 → 是否需复核 → 当前相关性与必要约束 → 最近引用与有上限的频次加分。引用只影响常用程度，不能刷新 last_confirmed_at 或 expires_at。周期阈值配置化并评测，不把固定天数宣称为行业标准。

纠正、撤销、过期和策略变化通过权威 revision 使缓存和摘要失效；缓存命中仍检查时间。生成前核对版本，关键计划输出前检查必要变更。遗忘中断后续旧上下文使用，但不因此重放或撤销已完成 Java 操作。

若旧摘要/助手文本中的偏好无法可靠定位，重建模型上下文基线；保留页面档案和独立业务确认状态。不能粗暴删除仍含待执行业务任务的 Checkpoint。

清空时提高 write_epoch，作废旧候选与来源任务，设置来源重放边界，防止聊天历史重新灌回已遗忘条目。单项撤销也保留必要删除边界。忘记 Memory 与删除聊天是不同产品操作；在线清理不等于立即清除所有备份，保留和恢复策略需覆盖派生与备份。

### 12.1 撤销后怎样使缓存、摘要和旧上下文失效

补充核对日期：2026-10-25。以下为目标协议，仍未实施代码。

撤销事务同时提交：memory.status=REVOKED、memory.version 增加、所属用户机构 profile.revision 增加、审计和 memory.revoked Outbox。正式撤销生效不依赖缓存删除成功；前端可区分“停止使用已生效”与“历史正文清理状态”。

所有可复用派生对象都携带来源版本：缓存键含 subject/org/purpose/revision；摘要和上下文快照含依赖的 memory_id/version、来源 profile revision 和模型上下文基线。依赖清单按可能传播的注入集合保守记录，摘要合并时继承前摘要与来源消息的依赖，不只依赖模型声明的 used_memory_refs。教练线程如使用学员 Memory，必须登记学员 profile 依赖，不能只按线程拥有者清理。

读取先检查权威 revision；旧缓存即使仍存在也不能命中当前版本。旧摘要一旦依赖失效，整份停用或从已过滤的有效来源重建；第一版可采用用户机构范围修订号做保守整体失效，不承诺依靠 LLM 精确删除一句话。权威检查不可仅依赖异步推送或可能陈旧的 revision 缓存；检查不可用时停止重用这些派生个性化数据。

恢复 Checkpoint 前检查上下文版本。流程执行状态、独立确认表和模型输入分别处理：保留待确认 ID、业务执行进度和工具幂等标识，丢弃或重建陈旧消息上下文。历史 user/assistant/tool 正文可能已经含有被撤销内容，不能仅剔除 Memory 专用块后原样发送。可靠来源过滤不可行时，切换到新的模型上下文基线，并从业务查询恢复必要背景；重建消息必须保持 tool call/result 配对，不能重放 Java 写操作。

每次模型调用前校验依赖；撤销通知促使在途运行取消或重建。最终回答、摘要和 Checkpoint 派生快照的发布，还需在与撤销协调的短事务/提交屏障中再次核对 expected_revision，使旧版本结果无法覆盖新版本。校验后直接异步无条件写入仍存在竞态；仅有摘要自己的 summary_version 也无法替代 Memory 撤销屏障。

例：运行 A 依据 revision=12 生成摘要，撤销使 revision=13，A 返回后必须拒绝发布其 revision=12 摘要。不能因为旧摘要已删除、表里没有行，就允许它重新插入。Outbox 消费幂等重试负责后续物理清理，失败告警不取消已经提交的撤销。

撤销之前已发送给模型或已向用户展示的内容不能撤回。撤销后的可执行保证是拒绝陈旧上下文继续复用或发布新结果，并处理仍在运行的请求；流式内容按 run/上下文版本丢弃迟到片段。页面历史可继续用于用户查阅，但刷新或继续聊天时由服务端重建模型输入，不从前端原样回传旧历史作为有效上下文。用户重新明确提供的信息可用于当前轮，跨会话重新保存仍需新授权。

当前代码采用提交撤销后尽力清理：MemoryService 调用 invalidate_for_subject，删除该主体摘要及历史提交记录，再删除发现线程的 Checkpoint 三张关联表。尚无上述 revision 屏障与可靠撤销事件；异常只记录日志，可能留下旧派生数据，物理删除也可能影响待确认图恢复。因此不能将当前清理路径描述为完整实现了本目标协议。

## 13. 前端、异常与可观测性

候选卡片展示动作、前后差异、来源、机构、条件和期限。候选批准结果与普通聊天分别绑定消息 ID 和来源 ID；迟到通知按 sequence/version 合并，不覆盖正在生成的新回答。

Memory 读取失败不等于没有记忆：普通沟通可降级为通用回答，必要约束不明的训练计划应追问或暂停。提取失败可重试且不阻断普通回答；候选暂不可用不得声称已记住。批准版本冲突展示最新差异重确认。

记录提取成功/失败、证据不匹配、批准拒绝编辑率、重复/覆盖冲突、注入量、引用量、复核、失效再注入、Outbox 积压和清理延迟。日志使用脱敏身份与 ID，不记录完整偏好和用户原文。用户确认率不能替代准确率。

## 14. 实施顺序与验收

1. 定义 Registry、单值/集合、条件与用户体验，落实来源消息档案。
2. 升级数据结构与统一命令服务，先解决盲目覆盖、版本、幂等和批准原子性。
3. 公共入口接入两阶段提取、Outbox 与候选差异展示。
4. ContextBuilder 先覆盖普通对话和本人计划，再覆盖预约、客服、文档与授权代读。
5. 接入来源支持、版本级使用账本、复核/冷却和派生失效。
6. 并发与端到端验收、观测、小范围启用，再逐步切换。

迁移保留原 ID、确认来源和版本；只确定性映射已知旧 key。不明确项标记 legacy/needs_review，默认不进入新的自动上下文，邀请用户确认拆分。停止旧写入口后调整旧唯一约束；密文迁移确认后清除旧明文。没有历史正文快照的被覆盖旧值不保证可恢复。

重点验收：多动作/多时间共存；可用与偏爱分开；临时输入不改长期；同义去重与否定；普通对话可提取；未批准不跨会话；组合提交与并发冲突；响应丢失重试；跨用户机构隔离；引用和支持计数幂等；旧版本迟到；到期不续期；遗忘后旧任务、摘要、缓存不复活；教练授权代读；模型伪造引用拒绝；关键约束确定性校验。

这些是后续实施需要通过的验收项目，本文未声称测试已经完成。初期继续在现有 Python 服务中分模块，Java 保留业务授权和业务事实职责，不必另拆微服务。

## 15. 适合复述的设计说明

“我的 Memory 设计保留五类，但在每类下面用受控维度和独立条目支持多个偏好。模型先从用户明确表达提取结构化事实和来源，服务端规范化后查询相关旧项；规则识别重复与新增，模型辅助理解替换和条件关系，有歧义就澄清。变更经用户确认，按目标版本把正式记忆、候选、审计和通知原子提交。使用时统一按身份、机构、用途、有效期与条件构造上下文，当前输入优先。用户支持、知识引用和个性化使用分别记录；引用只说明使用活跃度，不等于重新确认。遗忘结合有效期、复核和冷却，并处理缓存、摘要与旧任务，避免已撤销信息重新进入上下文。”
