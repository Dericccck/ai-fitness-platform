**可以在面试中说“文档处理方案参考了 Docling”，而且可以具体讲清楚参考了什么。** 比较准确的表述是：

> 我参考了 Docling 的文档解析设计：针对不同格式使用合适的解析方式，把正文、标题、表格、图片统一成带来源信息的结构化内容，再结合健身知识的特点，设计清洗、父子分块、审核和向量入库流程。

你自己的工作可以重点讲：**动作知识如何组织、适用条件和注意事项如何保留、图片知识如何审核，以及异步任务和版本发布如何保证可靠。**

根据我们之前整理的[最终设计文档](/Users/a1-6/Desktop/fitness-backend/docs/健身项目_RAG文档处理与入库最终设计_20261019.md)，Docling 主链属于目标改造方案。因此，目前面试用“调研、参考并设计了方案”这个口径；实际完成接入和验证后，再说“项目使用了 Docling”。

下面沿着这份方案讲，使用假设的《坐姿划船器械指南》作为贯穿示例。

**先明确：Docling 是组织解析流程的框架，里面可以调用多种模型。**

它会根据文件格式选择解析后端和处理管线，最终输出统一的结构化文档。[官方架构说明](https://docling-project.github.io/docling/concepts/architecture/)

可以把整个流程记成：

```text
上传原件
  ↓
保存到 MinIO/S3，创建处理任务
  ↓
RabbitMQ 分发，Worker 异步处理
  ↓
按文件类型提取内容
  ↓
统一成：标题、段落、列表、表格、图片及其来源
  ↓
清洗、检查、组织父子块、审核
  ↓
Embedding 模型生成子块向量
  ↓
PostgreSQL + pgvector 写入候选索引
  ↓
检查通过，发布新版本
```

模型主要出现在两个地方：**前半段从页面或图片中恢复内容，后半段把已经整理好的文字转换成检索向量。**

---

**Docling 里的几个模型，分别解决不同问题。**

下面的默认配置以我核对的 **Docling v2.140.0** 为准。

| 模型或组件 | 输入是什么 | 输出是什么 | 在你的方案中负责什么 |
|---|---|---|---|
| **Heron 版面模型** | PDF 页面的图像 | 标题、正文、表格、图片等区域的位置和类别 | 判断页面各部分是什么 |
| **RapidOCR 中的文字检测、识别模型** | 扫描页或图片区域 | 文字、文字框坐标及识别信息 | 把图片中的字读出来 |
| **TableFormer 表格结构模型** | 表格区域，结合提取出的文字 | 行列、单元格、合并关系及内容对应关系 | 恢复 PDF 表格结构 |
| **CodeFormulaV2**，可选 | 公式或代码区域图像 | LaTeX 公式或代码文本 | 处理需要进一步识别的公式、代码 |
| **SmolVLM、Granite Vision 等**，可选 | 图片 | 图片的文字描述 | 辅助理解图片展示的内容 |

Heron 是该版本默认的版面模型，属于 RT-DETR 系列。它能定位标题、正文、表格、页眉、页脚等区域。比如输出“这里有一个表格，坐标范围是……”，具体单元格由后续环节处理。[Heron 官方模型说明](https://huggingface.co/docling-project/docling-layout-heron)

TableFormer 负责恢复表格结构，并将原生文字或 OCR 文字对应到单元格。我们的方案选择 Accurate 模式。[TableFormer 实现](https://github.com/docling-project/docling/blob/v2.140.0/docling/models/stages/table_structure/table_structure_model.py)

公式识别和图片描述属于可选增强功能，需要显式开启。[官方增强功能说明](https://docling-project.github.io/docling/usage/enrichments/)

关于 OCR，再具体一点：

**RapidOCR 是 OCR 引擎，它里面还会加载具体的模型。** 例如固定为 RapidOCR v3.9.1、ONNX Runtime、中文、small 这一组配置，可以使用：

```text
PP-OCRv6_det_small.onnx
    找到图片中每一行文字的位置

ch_ppocr_mobile_v2.0_cls_mobile.onnx
    判断文字行方向，需要时使用

PP-OCRv6_rec_small.onnx
    将文字区域的像素识别成字符串
```

这是一个明确的配置组合。其他版本、语言和配置可能选择不同模型，部署时需要固定版本、模型文件及哈希。[RapidOCR 官方模型配置](https://github.com/RapidAI/RapidOCR/blob/v3.9.1/python/rapidocr/default_models.yaml)

还要区分两件事：

- **Docling 默认支持自动选择 OCR 引擎。** RapidOCR 是我们在项目方案中显式选定的引擎。[配置源码](https://github.com/docling-project/docling/blob/v2.140.0/docling/datamodel/pipeline_options.py)
- 你如果看到 **Granite-Docling-258M**，它是另一条可选视觉语言模型管线使用的模型，可以将整页图像转换成结构化文档。我们这份方案使用标准 PDF 管线，不需要每份文件都调用它。[官方模型预设](https://github.com/docling-project/docling/blob/v2.140.0/docling/datamodel/stage_model_specs.py)

下面看这些组件如何处理不同文件。

---

**Word：首先利用文件本身已有的结构。**

假设上传的是 `坐姿划船指南.docx`，里面有：

```text
标题：坐姿划船
  小标题：器械调整
  编号列表：动作步骤
  小标题：注意事项
  表格：器械型号与参数
  图片：座椅调节机构示意图
```

处理过程是：

```text
读取 DOCX 包内的 XML
  ↓
读取段落、标题样式、列表、表格
  ↓
通过图片关系找到图片文件
  ↓
构造章节结构，并关联图片、图注和表格
```

这里的正文、标题和原生表格，通常依靠文件结构解析，**不需要先把 Word 截成图片再 OCR**。

具体来说：

- 标题样式帮助确定章节层级。
- 编号信息帮助保留完整步骤列表。
- 表格的单元格结构和合并信息来自 XML。
- 图片通过文档中的关系 ID 找到实际文件。
- 原生公式可以从公式对象中提取表达式。

这些处理在 Docling 的 Word 后端中有对应实现。[Word 后端源码](https://github.com/docling-project/docling/blob/v2.140.0/docling/backend/msword_backend.py)

但 Word 中嵌入的图片，还要进入我们自己的图片处理分支：

| 图片内容 | 处理方式 |
|---|---|
| 图片上写着“座椅调节杆” | 可以用 OCR 提取文字 |
| 图片是一张器械参数表截图 | 按图片表格处理，需要识字和恢复表格结构 |
| 图片展示动作姿态，没有文字 | OCR 无法提取姿态含义，需要图注、人工说明或视觉模型辅助 |
| 装饰图片、Logo | 保存必要资产关系，通常不作为知识正文参与检索 |

**从 Word 中取出图片文件，只完成了图片提取；图片内容还需要单独处理。**

最终得到的结构大致是：

```text
章节：坐姿划船
  段落：器械调整说明
  列表：完整动作步骤
  段落：注意事项
  表格：器械参数
  图片：image_001
    图注：座椅调节机构
    来源：所属章节和对象位置
```

Word 不一定有稳定页码，来源定位可以使用章节路径、段落 ID、表格和图片 ID；需要固定页码时，再绑定特定渲染版本。

---

**Markdown：通过语法解析得到章节和内容节点。**

例如：

```markdown
# 器械指南

## 坐姿划船

### 器械调整
调整说明……

### 动作步骤
1. 第一步……
2. 第二步……

### 注意事项
注意事项……

![座椅调节机构](images/seat.png)
```

我们的方案使用 `markdown-it-py`：

```text
读取 Markdown
  ↓
解析成语法节点
  ↓
根据标题等级构建章节树
  ↓
保留段落、列表、表格、代码块和图片引用
  ↓
通过附件清单读取图片
```

这里主要是语法解析，不需要 OCR 或大模型。

例如遇到 `## 坐姿划船`，建立一个二级章节；后面的 `### 动作步骤` 挂在它下面。代码块中的 `#` 会被保留为代码内容。

图片节点里的：

```markdown
![座椅调节机构](images/seat.png)
```

只能直接提供“替代文字”和图片路径。系统还要找到图片本体，然后进入前面讲的图片分支。

所以：

> Markdown 的正文和结构可以直接解析；图片里额外包含的文字或动作信息，需要单独处理。

---

**原生 PDF：文字通常能直接读取，但页面结构需要恢复。**

假设这份指南导出成 PDF，可以选中文字，页面还有双栏排版、表格和图片。

PDF 中可能存储的是：

```text
文字：“坐姿划船”
坐标：页面上方某位置
字体：某字体
字号：18
```

它不一定明确告诉你“这是二级标题，下面这些内容属于它”。

处理流程是：

```text
PDF 后端提取原生文字、字体和坐标
  ↓
页面渲染后交给 Heron
  ↓
定位标题、正文、表格、图片等区域
  ↓
将文字分配到对应区域
  ↓
表格区域交给 TableFormer
  ↓
结合位置关系恢复阅读顺序
  ↓
结合书签、编号、字体等推断标题层级
  ↓
输出结构化文档
```

这里用到模型的地方是：

- **Heron：识别版面区域。**
- **TableFormer：处理表格结构。**
- 某个图片区域中还有文字时，再补充 **OCR**。

例如左右两栏正文，要结合版面关系组织阅读顺序，避免将左栏的一句话和右栏的一句话交替拼接。

对于 PDF 标题层级推断，我们的方案需要显式配置并检查结果，不能把“检测出标题区域”直接等同于“已经正确恢复整棵章节树”。

---

**扫描 PDF：文字首先要从页面图像中识别出来。**

假设这份指南是纸质书扫描而来，每页基本都是一张图片。

流程变成：

```text
渲染页面
  ↓
Heron 定位正文、标题、表格、图片
  ↓
RapidOCR 检测文字并识别内容
  ↓
得到文字及坐标
  ↓
TableFormer 恢复表格结构并关联文字
  ↓
恢复阅读顺序、章节关系
  ↓
输出结构化文档
```

举一个假设的器械参数表：

| 器械型号 | 净重（kg） |
|---|---:|
| R01 | 85 |
| R02 | 110 |

不同模型的工作是：

```text
Heron：
“这一片区域是表格。”

OCR：
“识别到了器械型号、净重、kg、R01、85、R02、110。”

TableFormer：
“这是两列三行，85 对应 R01 的净重。”
```

**识别出了所有文字，并不意味着表格已经解析正确。** 如果 `85` 被放到了 R02 那一行，检索得到的知识仍然是错的。

所以还要用程序检查行列对应、表头、单位和关键数字。识别失败的关键内容进入复核流程，不能直接忽略后发布。

---

**文字和图片混合的 PDF：在页面内部按区域处理。**

同一页可能包含：

```text
上半部分：原生文字“器械调整说明”
中间部分：扫描进去的参数表
下半部分：动作示意图片
```

不能只根据“这一页能提取到文字”，就认定整页都不需要 OCR。

我们的目标处理方式是：

| 区域 | 走哪条路径 |
|---|---|
| 可用的原生正文 | 直接提取文字，再结合版面组织 |
| 扫描参数表 | OCR 读取文字，TableFormer 恢复单元格 |
| 图片内的标签文字 | OCR 提取，并关联图片 |
| 图片中的动作含义 | 进入图片知识处理和审核 |

Docling 的区域 OCR 配置可以结合 PDF 原生文字信息，决定哪些区域需要补充 OCR。[区域 OCR 配置](https://github.com/docling-project/docling/blob/v2.140.0/docling/datamodel/pipeline_options.py)

补 OCR 后，还要避免重复：

```text
原生文字层已经存在一句话
OCR 又在相同位置识别出同一句话
```

合并时同时比较位置和文字内容，关键数字、单位及否定词还要核对；不能把两份结果直接拼起来。

---

**表格和图片，最终都要形成适合检索的内容。**

表格在三种来源中的解析方式不同：

```text
Word 原生表格 → 读取单元格结构
Markdown 表格 → 读取语法节点
PDF / 图片表格 → 结构模型 + 原生文字或 OCR
```

它们最后应统一保存：

```text
表格标题
表头及层级
单元格内容
行列位置
跨行、跨列关系
单位、脚注
来源位置
```

然后从这个结构生成检索文本。例如前面的参数表可以生成：

```text
器械指南 / 坐姿划船 / 器械参数

器械型号：R01
净重：85 kg
```

一张大表需要拆分时，按完整行或相关行组拆，每组携带必要表头、单位和说明。原始网格结构继续保留，方便展示、核查和计算。

图片则要区分“文字”和“视觉含义”：

- 图片上的器械编号，可以通过 OCR 提取。
- 图片展示的手柄位置、动作阶段，可以由视觉模型生成候选描述。
- 图片独有的动作知识，按你的目标方案，需要专业审核后才能成为正式知识。

审核通过后，可以保存为：

```text
图片：image_001
所属章节：坐姿划船 / 器械调整
原始图注：座椅调节机构
审核后的说明：……
来源：原文件及图片位置
```

后面参与文本向量化的是**图注和审核后的说明**，原图作为关联资产保留。这套方案中的文本 Embedding 不直接读取图片像素。

---

**不同格式完成解析后，就进入同一条清洗和分块流程。**

此时处理对象应当是结构节点：

```text
文档
  └─ 坐姿划船
      ├─ 适用范围
      ├─ 器械调整
      ├─ 动作步骤
      ├─ 注意事项
      ├─ 参数表
      └─ 图片及说明
```

清洗主要通过程序规则完成。例如：

- **页眉、页脚：** 结合版面标签、页面边缘位置和跨页重复情况识别，移出用于检索的正文，保留原始记录。
- **错误断行：** 只在同段、同栏、没有列表边界的情况下合并。
- **重复文字层：** 根据位置和内容对应关系去重。
- **乱码：** 先尝试重新提取或 OCR，仍无法恢复则标记待处理。
- **表格：** 保留单位、表头、脚注和单元格对应关系。

这样不需要让大模型把每段正文重新写一遍，也能保留原文的关键限定条件。

接下来才生成父子块。

例如，“坐姿划船”这一业务章节作为父块：

```text
父块 P1：坐姿划船
  保存完整章节结构和来源关系

子块 C1：适用范围
子块 C2：器械调整
子块 C3：完整动作步骤或连续步骤组
子块 C4：注意事项
子块 C5：参数表的一组完整行
子块 C6：审核后的图片说明
```

具体分块顺序是：

```text
标题和业务章节确定父块
  ↓
段落、列表、表格行组确定基本内容单元
  ↓
合并主题相同、上下文一致的小单元
  ↓
用 Embedding 模型的 tokenizer 检查长度
  ↓
超长时再沿完整步骤、句子等边界拆分
```

**标题结构决定内容边界，父子关系决定如何补上下文，Token 预算决定单次输入大小。**

例如 C3 是动作步骤，就保存它依赖的适用范围和注意事项 ID。将来命中 C3，可以补回这些内容，避免只给出动作步骤而丢失限定条件。

这里的结构分块由项目规则实现，不要求额外调用一个“分块大模型”。

---

**到了这一步，才调用 Embedding 模型生成向量。**

以 **BGE-M3** 为例，它可以把一段文字编码成 **1024 维向量**。[BGE-M3 官方模型说明](https://huggingface.co/BAAI/bge-m3)

你的代码支持可配置的本地或远端 Embedding，默认期望 1024 维；这里用 BGE-M3 举例，不代表已经确认当前运行环境加载的就是它。

对子块 C2，实际输入可以是：

```text
器械指南 / 坐姿划船 / 器械调整

适用条件：……
调整步骤：……
相关说明：……
```

模型输出类似：

```text
[0.012, -0.038, 0.026, ...]
```

这组数字用于比较语义相似度。原文、来源和父子关系仍然需要单独保存。

按你的方案：

- 子块生成向量，用于精确召回。
- 父块保存完整上下文和结构关系。
- 子块保留标题路径、来源节点、`parent_id` 和必要上下文引用。
- 图片通过审核后的文字说明参与文本检索。

审核应绑定确定的解析和分块结果。批准后直接对这份结果向量化，避免重新 OCR 导致实际入库内容与审核内容不同。

---

**最后的“入库”，需要把文字、关系、权限和向量一起组织好。**

你继续使用 PostgreSQL＋pgvector，可以保存：

| 数据 | 用途 |
|---|---|
| 文档 ID、版本、原件哈希 | 确认来自哪份文件 |
| 父块内容与结构 | 补充上下文 |
| 子块原文与标题路径 | 检索和回答证据 |
| `parent_id`、上下文引用 | 关联适用范围和注意事项 |
| 页码、坐标或来源节点 | 展示引用、追溯原文 |
| 图片和表格引用 | 展示完整内容 |
| 权限信息 | 限制可检索范围 |
| Embedding 向量 | 语义检索 |
| 词法索引 | 支持名称、型号等文字匹配 |
| 解析器、模型和规则版本 | 重现处理结果 |

发布过程是：

```text
生成全部子块向量
  ↓
检查数量、维度、内容与来源关系
  ↓
写入候选索引构建
  ↓
检查权限、审批状态和检索结果
  ↓
在数据库事务中切换 active_build_id
```

中间一批向量生成失败时，候选构建不能发布，旧版本继续提供服务。

用户提问后，还会经过“问题向量化、召回、融合、Reranker 排序、补上下文、回答模型生成答案”。其中 **Reranker 和回答模型属于查询阶段**，与前面的文件解析模型分工不同。

面试时，可以按下面这一段展开：

> 我的健身知识库处理方案参考了 Docling 的分层解析设计。上传后先保存原件，通过 RabbitMQ 异步处理。Word 和 Markdown 优先读取原生结构；PDF 使用版面模型定位标题、正文、表格和图片，对扫描区域补 OCR，再用表格结构模型恢复单元格关系。
>
> 各种文件统一成带来源信息的结构节点后，我再做清洗和业务分块。以一个健身动作为父块，下面按步骤、注意事项、表格和图示说明生成子块，并保留它们对适用条件的依赖。Token 用于控制大小，主要边界来自标题和完整内容单元。
>
> 审核通过后，使用 Embedding 模型生成子块向量，和原文、父子关系、权限、来源一起写入 PostgreSQL＋pgvector。新索引检查通过后再切换版本，确保检索能够找到相关内容，也能补齐动作知识需要的上下文。

---

有。对于你的健身项目，应该把它设计成一套完整的**知识文档生命周期管理**：上传、去重、更新、审核、发布、撤回、重建和回滚。

你前面问的三种情况，加上删除、权限变更、分块调整、失败重试等，都可以按照同一套原则处理：

> **原件决定是否需要重新解析；最终输入文字和 Embedding 配置决定是否需要重新计算向量；内容关系、权限和版本变化决定是否需要更新发布结果。**

下面讲的是对我们现有文档中“目标方案”的补充设计。

**先把几种身份和版本区分清楚，系统才能判断哪些工作可以复用。**

假设有一份《坐姿划船器械指南》，建议记录这些信息：

| 信息 | 例子 | 解决什么问题 |
|---|---|---|
| 逻辑文档 ID | `doc_001` | 确定这是哪一份指南，修改后仍属于同一份文档 |
| 原件哈希 | 文件字节的 SHA-256 | 判断上传的文件是否完全一样 |
| 文档版本 | `revision_1`、`revision_2` | 记录原件和业务内容的变化 |
| 处理配置版本 | 解析器、OCR、清洗和分块配置 | 判断之前的处理结果是否还能使用 |
| 子块输入哈希 | 最终送入 Embedding 的文字哈希 | 判断某个子块的向量是否可以复用 |
| Embedding 配置 ID | 模型固定版本、维度、输入处理参数等 | 确认向量来自哪套编码规则 |
| 索引构建 ID | `build_001`、`build_002` | 标记一套可发布、可回滚的检索结果 |

这里有个容易忽略的地方：**文件名不能作为文档身份。**

管理员更新现有文档时，上传请求应携带 `document_id`；从外部系统同步时，应使用稳定的来源 ID。不能因为两个文件都叫“动作指南.pdf”，就自动覆盖。

---

**第一种情况：完全相同的文档又上传一次，正常情况下直接复用。**

前提是：处于同一个授权范围、对应同一份逻辑文档，而且要求使用的处理配置没有变化。

流程可以是：

```text
接收文件，同时计算 SHA-256
  ↓
查询该文档已有的原件哈希和处理状态
  ↓
发现文件相同、处理配置相同
  ↓
检查已有任务或已发布构建
  ↓
返回已有结果
```

具体还要区分已有状态：

| 已有状态 | 再次上传时怎么处理 |
|---|---|
| 已成功发布 | 返回已有文档和版本，不重复解析、向量化 |
| 正在处理 | 返回已有任务 ID，避免启动第二份相同任务 |
| 等待审核 | 返回已有待审核版本 |
| 上次处理失败 | 按重试规则恢复任务，不能当作已经成功 |
| 原件相同，但要求升级解析或 Embedding 配置 | 创建新的处理或索引构建 |

例如用户连续点击两次上传，或者 RabbitMQ 重复投递消息，应通过数据库唯一约束和幂等处理，让它们归到同一个任务。只在代码里“先查一下有没有”不够，因为两个请求可能同时查到不存在。

另外，**原件哈希相同只代表文件字节相同**。如果 Markdown 引用了单独上传的图片，还需要把附件清单及图片哈希纳入输入指纹，否则 Markdown 没变、图片换了，系统可能漏掉更新。

去重默认在机构或知识库的授权范围内进行。复用计算结果也必须保留当前文档自己的来源和权限。

---

**第二种情况：文档小幅修改，通常重新处理内容，但只重新计算发生变化的向量。**

这里要把两件事分开：

- **重新解析文档：** 得到最新的正文、结构、表格、图片和来源位置。
- **重新计算向量：** 对最终输入发生变化的子块调用 Embedding。

我们的方案可以先采用稳定、容易验证的做法：

```text
新原件形成 revision_2
  ↓
重新解析、清洗并生成父子块
  ↓
计算每个子块的最终 Embedding 输入哈希
  ↓
与已有向量缓存比较
  ├─ 输入和 Embedding 配置都相同：复用向量
  └─ 输入或 Embedding 配置发生变化：重新计算
  ↓
建立完整的新构建，审核、检查后发布
```

**不需要为了实现向量增量更新，就先实现复杂的 PDF 增量解析。** 可以全文件重新解析，在向量计算这一层节省重复工作。

假设原来有四个子块：

```text
C1：器械调整
C2：动作步骤
C3：注意事项
C4：器械参数表
```

这次只修改 C3，并且其他子块最终输入没有受到影响：

| 子块 | 新版本处理 |
|---|---|
| C1 | 复用已有向量 |
| C2 | 复用已有向量 |
| C3 | 重新计算向量 |
| C4 | 复用已有向量 |

但是，**不能承诺“改了一段，就只重算一个块”**。下面这些修改可能影响多个子块：

- 修改章节标题，而标题路径被加进了所有子块的输入。
- 修改适用条件，而多个子块都携带这个条件。
- 修改表头或单位，导致多个表格行组的输入变化。
- 增删内容后，分块边界发生变化。

判断依据应当是**真正提交给 Embedding 的完整文字**。

例如：

```text
器械指南 / 坐姿划船 / 动作步骤
适用条件：……
步骤正文：……
```

即使“步骤正文”没有变，只要前面的标题或适用条件变了，这个输入就变了。

向量缓存键可以按下面的结构生成：

```text
授权隔离范围
＋ Embedding 配置 ID
＋ 输入角色（document）
＋ 最终输入文字哈希
```

这些字段用确定的结构序列化后再计算哈希。Embedding 配置需要包括模型固定版本，以及实际影响输出的维度、前缀、池化、归一化和截断等参数。文本哈希与模型命名空间结合，也是现有框架中常见的 Embedding 缓存方式。[LangChain 官方缓存说明](https://docs.langchain.com/oss/python/integrations/embeddings)

这里还有两个工程细节：

1. **新构建仍然要包含全部有效子块。**  
   即使只计算了 C3，也要让 C1、C2、C4 的复用向量正确关联到新版本。

2. **复用向量不等于复用旧来源和旧父块。**  
   页码、坐标、父块内容发生变化时，这些信息必须更新，避免查到新文档却引用旧页码。

例如，只在 Word 中调整了排版，文件哈希可能变化；重新解析后发现所有 Embedding 输入都没变，就可以复用全部向量，同时更新引用位置。

---

**第三种情况：模型变了，要先明确变的是哪一个模型。**

| 发生变化的组件 | 是否重新解析 | 是否重新计算文档向量 |
|---|---|---|
| 回答用户的生成模型 | 通常不用 | 通常不用 |
| Reranker 重排模型 | 不用 | 通常不用 |
| Embedding 模型或其权重版本 | 通常不用重新 OCR | 通常需要为迁移范围内的全部有效子块生成新向量 |
| OCR、版面或表格识别模型 | 对要迁移的文档重新解析 | 比较新旧最终输入，变化的部分才重算 |
| 图片描述模型 | 重新生成需要更新的图片描述并审核 | 描述变化后，相关子块重算 |
| 清洗、分块规则 | 从可复用的结构化内容重新处理 | 新生成或输入变化的子块重算 |
| 向量数据库的索引参数 | 不用 | 通常不用调用 Embedding，可能需要重建数据库索引 |

例如，换了最终回答问题的大模型，知识库里的文字向量通常可以继续使用。

但如果从 Embedding 模型 A 换成模型 B，就要按新的向量空间处理。**即使两个模型都输出 1024 维，也不能默认它们的向量可以直接比较。**

查询侧也必须使用与目标文档向量空间匹配的编码配置：

```text
模型 A 编码用户问题 → 检索 A 的文档向量

模型 B 编码用户问题 → 检索 B 的文档向量
```

模型名字没变，也不一定代表配置没变。重新微调了权重，或者服务端同名模型被替换，都需要按新的模型版本管理。

---

**如果更换 Embedding 模型，应该在后台准备新索引，再整体切换。**

对于你的 PostgreSQL＋pgvector 方案，可以这样实施。

**第一步，记录当前可用的整套查询配置。**

```text
当前模型配置：embedding_A
当前索引版本：release_A
当前文档构建清单：……
```

一套发布结果需要明确绑定模型配置、向量存储位置，以及各文档使用的构建版本。

**第二步，为模型 B 准备隔离的向量存储和索引。**

```text
A：继续处理线上查询
B：后台构建，尚未对普通查询生效
```

如果维度不同，给 B 准备匹配维度的向量列或表及索引。即使维度相同，也按模型配置隔离，避免误查。

pgvector 支持相应的分模型存储和索引方式；索引需要与向量维度匹配。[pgvector 官方说明](https://github.com/pgvector/pgvector#can-i-store-vectors-with-different-dimensions-in-the-same-column)

**第三步，读取已审核的子块文字，批量调用模型 B。**

通常可以直接使用已经保存的解析和分块结果：

```text
已审核的子块文字
  ↓
检查新模型的输入格式和 Token 上限
  ↓
必要时重新分块
  ↓
模型 B 生成向量
  ↓
写入 B 的候选构建
```

因此，换 Embedding 模型通常不需要把原始扫描 PDF 再 OCR 一遍。

迁移范围通常是**当前需要提供检索的有效知识**。保留用于审计的历史版本，可以按业务需要决定是否迁移。

**第四步，记录进度，支持失败重试。**

任务按子块或批次记录成功、失败状态。中途失败时，只补齐缺失结果。

如果 B 有一批向量生成失败，不能用 A 的向量填补；B 必须完整通过检查才能发布。

**第五步，处理重建期间发生的内容变化。**

这是生产迁移最容易遗漏的部分。

假设 B 正在处理旧快照，这时管理员：

- 更新了一份动作指南；
- 新增了一份器械说明；
- 删除了一份过期文件。

这些变更都需要通过可靠的变更记录，例如事务 Outbox，同步到 B。B 不能最后发布成“几个小时前的知识库”。

对于删除和撤权，线上查询还应检查当前的删除状态和权限，不能等重建结束才生效。

**第六步，验证并切换。**

需要检查：

- 有效文档和子块是否齐全；
- 向量维度、模型配置是否一致；
- 新版本父子关系和引用是否正确；
- 删除和权限变化是否已经落实；
- 固定评测问题的召回、引用、延迟和成本是否符合要求。

切换前，短暂暂停知识版本的发布，核对 B 已应用所有应包含的变更，再在数据库事务中切换整套路由。

不能仅凭“RabbitMQ 队列空了”判断完成，还要确认任务已经执行成功、文档版本清单一致。

每次查询开始时固定使用一套配置，保证这次请求中的问题向量、文档向量和父块属于匹配的版本。

保留旧索引、后台生成新向量、验证后切换，是成熟的模型迁移方式。[模型迁移参考](https://qdrant.tech/documentation/tutorials-operations/embedding-model-migration/)

**第七步，保留可用的回滚窗口。**

回滚窗口内，如果还允许继续发布新内容，A、B 都需要继续同步这些变化。

否则，过几天直接切回 A，可能会重新出现已删除内容，或者丢掉最近的更新。**只保存一份旧索引快照，并不足以保证能安全回滚。**

---

**除了你提到的三种情况，还有下面这些需要明确处理。**

| 情况 | 健身项目中的例子 | 应该怎样处理 |
|---|---|---|
| 只改展示信息 | 修改上传备注、管理端显示名称 | 更新元数据；如果它没有进入 Embedding 输入，就不用重算 |
| 修改知识标题 | “器械指南”改成更具体的标题 | 如果标题加入了子块输入，相关子块重算 |
| 修改权限 | 某指南改为仅教练可见 | 更新权限并立即约束查询，无须因此重算向量 |
| 生效或到期 | 一份场馆规则下周生效 | 保存生效时间并在查询时过滤，可以提前完成向量化 |
| 删除或撤回文档 | 发现某份动作资料存在错误 | 立即停止召回，保留必要历史记录，再异步清理无引用数据 |
| 删除文档中的章节 | 新版删除某个器械的使用说明 | 新构建中排除相关子块，发布后旧块不再被召回 |
| 分块规则调整 | 原来的固定字符分块改成标题和父子分块 | 从结构化内容重新分块；最终输入相同的向量仍可复用 |
| 图片或附件更新 | Markdown 正文没变，但动作图片换了 | 根据附件哈希识别变化，重新处理相关图片和引用 |
| 图片审核说明修改 | 专业审核纠正了图片说明 | 更新相关知识制品，重算输入变化的子块 |
| 文档转移到另一知识库 | 从测试库发布到正式库 | 建立目标库的来源、权限和发布关系；符合条件时复用计算结果 |
| 任务中断或重复投递 | Worker 重启、MQ 重投 | 幂等恢复，复用成功阶段，避免产生重复可见记录 |
| 两个人同时修改 | 教练和管理员分别上传两个新版本 | 使用版本检查，防止较旧任务覆盖较新版本 |
| 恢复历史版本 | 新版指南有问题，恢复上一版 | 发布一次明确的恢复操作，校验当前模型、权限和有效期 |
| 文件内容高度相似 | 通用指南和特殊人群指南只有少数区别 | 可以标记待核查，不能直接按相似度合并 |

其中有四类特别适合在面试中展开。

**删除内容时，必须让旧内容退出检索。**

假设旧文档有 C1、C2、C3，新版本删除了 C2：

```text
旧构建：C1、C2、C3
新构建：C1、C3
```

发布新构建后，向量和词法两条检索路径都只查询新构建的有效块。旧 C2 即使暂时保留用于回滚，也不能继续参与普通查询。

父子块的查询也要绑定版本，避免子块已经更新，补回的却是旧父块。检索和回答缓存同样要随发布版本失效或使用新的缓存键。

**只改权限，不需要调用 Embedding，但权限必须立即生效。**

例如某文档原来所有会员可见，后来改成仅教练可见。向量值本身可以保留，但查询必须检查当前用户是否有权访问。

已经缓存的搜索结果也要重新校验权限。否则数据库权限更新了，缓存仍可能返回原内容。

**并发更新时，不能让“最后跑完的任务”自动获胜。**

例如：

```text
版本 2：先上传，解析较慢
版本 3：后上传，先处理完成并发布
版本 2：随后才处理完成
```

版本 2 的任务不能覆盖版本 3。

任务需要携带源版本，发布时检查当前允许发布的目标版本；过期任务可以保存处理结果，但不能自动改变线上版本。用户明确要求恢复历史内容时，再创建一次正式的恢复操作。

**相似文档不能当作完全重复文档自动删除。**

健身资料可能只差一个适用条件、否定词或数值，业务含义就已经改变。

所以：

- 字节完全一致，可以做精确去重。
- 最终输入完全一致，可以复用向量。
- 只是语义相似，适合用于辅助发现重复或冲突，不能直接决定覆盖和删除。

面试时，可以这样串起来：

> 我把知识更新分成原件、解析制品、子块向量和发布版本几层管理。相同原件在相同处理配置下重复上传，会直接复用已有任务或结果；文档发生修改后，重新得到结构化内容，再根据子块最终输入的哈希复用未变化的向量。
>
> 如果更换 Embedding 模型，我会创建隔离的新索引，后台批量计算，持续同步期间的新增、更新和删除，评测通过后把查询编码器与索引配置一起切换。更换回答模型或 Reranker，通常不需要重算文档向量。
>
> 对删除、权限变化、失败重试和并发更新，我分别通过有效状态过滤、实时权限校验、幂等任务及版本检查处理，保证用户只能检索到当前允许使用的知识版本。
