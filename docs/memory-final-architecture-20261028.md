# 健身 Agent 长期 Memory 最终设计方案

日期：2026-10-28。本文以对话中讨论的**目标架构**为基础，统一确定首期范围、流程、数据契约、过期/撤销和异常处理。本次只编写方案，不检查项目当前实现，不修改业务代码或数据库。

这是一份可供设计评审和实施的方案，不承诺系统不存在缺陷。最终可靠性取决于源消息与任务落库、所有写入口遵守同一协议、供应商能力、端到端验收和线上监控。

## 1. 目标、原则与选型

目标是从用户对话中发现明确表达且可能跨会话有价值的信息，提出可审阅的记忆变更；用户确认后安全保存，并在以后的对话、训练计划或文档生成中按用途使用。五类下面允许多条，用户可以查询、纠正、撤销和管理。

最终选型：

- 正式数据、候选、用户决定、审计、可靠任务与通知以 PostgreSQL 为权威来源。
- 聊天消息先持久化，本轮交互完成后由异步 Worker 提取；用户当前输入立即用于本轮回答，不依赖后台记忆处理。
- 服务端 Registry 统一定义类型、维度、结构、归一、单值/集合及冲突规则。模型只做受限提取或语义辅助。
- 新旧比较先用结构化查询与确定性规则；模型处理不确定语义；pgvector 仅作为可控的辅助语义召回。
- 默认新增、修改及从普通表达推导的撤销需生成差异提案并确认；用户在管理页或对明确指定的记忆直接发出遗忘指令，可作为独立授权命令处理。
- 读取按用户、机构、授权、用途、有效期和适用条件选择；记忆正文是数据，不是系统指令或业务授权。
- 显式过期、待复核、低频冷却、用户撤销、物理删除是不同动作。使用频繁不自动延长有效期或证明事实可靠。
- 先上线结构化基线；向量能力设计为可选模块，经过召回与隐私评估后通过开关灰度启用。停用或失败时，不影响正式记忆存取和原子确认。

### 1.1 明确边界

聊天档案保存原话与页面消息；摘要压缩对话；Checkpoint 恢复 Agent State 与执行；正式 Memory 保存确认过的长期信息。它们相关联，不能相互代替。合同、预约状态、排班、教练可用性与课时等事实仍从业务系统读取；一次晚上预约不能自动推断长期晚上偏好。

模型不会因输入合规 JSON 就获得写权限。证据片段匹配原文也不证明语义一定正确；用户确认、程序校验和版本控制仍然必要。医学诊断、疼痛、支付凭据等不纳入本方案的五类低敏记忆；以后要支持其他敏感类别需独立设计。

### 1.2 基本产品策略

- 默认允许对符合范围的明确长期表达生成候选，提供“停止提取候选”和“停止使用已确认记忆”两个独立开关。
- 非明确表达、临时需求、引述他人、假设与助手/RAG 内容不能自动形成用户记忆。
- 普通运行只有可信完成后才发布自动候选；用户取消、运行失败或未提交完成时不自动发布。用户消息仍按聊天策略保存；已被独立接收的明确记忆管理命令按其命令结果处理，不假设用户没有表达过。
- 未批准候选不得作为跨会话正式事实。本轮用户刚明确提供的信息可以直接用于当前回答。
- 普通候选默认有效期 24 小时作为可配置初值；界面展示期限。候选过期后不自动批准，用户可通过明确交互重新提出。
- 正式条目默认不凭空设定统一过期日；用户明确的期限必须保存，需不需要复核由 slot 策略决定。

## 2. 五类与 Registry

| memory_type | slot_code 示例 | 基数与含义 |
|---|---|---|
| TRAINING_GOAL | goals、primary_goal | 目标可多项；主目标同一适用范围单值，用户明确主次才保存 |
| TRAINING_PREFERENCE | exercise_preference、training_environment、intensity | 动作按对象多项；强度按范围单值 |
| EQUIPMENT_AVAILABILITY | available_equipment | 按器械和场景多项；“喜欢”不等于“可用/拥有” |
| SCHEDULE_PREFERENCE | available_windows、preferred_windows、session_duration | 可用和偏爱分开；窗口多项；时长按范围单值 |
| COMMUNICATION_PREFERENCE | language、verbosity、output_format | 语言、篇幅和格式各自独立 |

Registry 每个 slot 定义：类型、值 Schema、SINGLE/SET、对象词典、范围字段、相关 slot、冲突域、时间语义、证据要求、有效期/复核策略、允许用途与规则版本。新增或改变 slot 必须评审并版本化。

正式条目的逻辑身份是 `subject_user_id + organization_id + slot_code + scope_key + item_key`：

- `scope_key`：适用地点、人群或其他条件的规范化身份。明确全局和条件未知要分开表达；用户没有给出条件时不得擅自断言所有场景均成立。
- `item_key`：集合里的对象，例如哑铃、杠铃或规范化时间窗口；单值维度在同一范围使用固定占位。标识由服务端计算，模型不能直接指定物理键。
- 对动作喜好，item 是动作本身，LIKE 改为 DISLIKE 时身份不变；不同动作可并存。
- 对时间窗口，窗口可作为集合成员。用户明确替换时，允许一个原子提案撤旧窗口、加新窗口。

机器可查询元数据与正文分开；身份采用带密钥且按租户/用途隔离的规范化指纹。规则或身份密钥换版本时必须兼容读取、检测重复并受控迁移，不能让同一对象变成另一个唯一身份。

## 3. 时间、器械与条件的规范化

时间的逻辑结构包括：日期或循环星期、本地时间区间或用户原始时段标签、时区来源、地点等限定条件、起止有效期。循环每周时间保留本地时区和星期，不永久换算为固定 UTC 小时；具体日期再处理时区/夏令时。明确区间统一比较边界，并对跨午夜区间拆分。用户只说“上午/晚上”，保留模糊标签，不编造具体小时；时区不能可靠确定时保留未知或询问。

可用与偏爱是不同事实。喜欢上午不等于实际上午有空；下午也可以不等于同样喜欢下午。没有查询到“不喜欢”的器械，不等于确认可以使用。

| 已有 | 新表达 | 处理 |
|---|---|---|
| 周末上午有空 | “周末下午也有空” | 保留上午，ADD 下午 |
| 周末上午有空 | “周末上午还是有空” | NOOP；可新增独立支持来源 |
| 周末上午有空 | “以后周末上午改成下午” | 展示撤旧加新的组合提案，确认后原子提交 |
| 多个窗口 | “以后改到下午” | 范围不明确，先澄清 |
| 工作日晚间有空 | “周二晚不行” | 对部分重叠、未知边界或例外规则先比较并按目录规则澄清；不因 key 不同直接假定无冲突 |
| 喜欢周末上午 | “下午也可以” | 保存上午偏爱及下午可用两条，不把“可以”当作“喜欢” |

如果精确窗口的局部移除确有明确边界，允许拆成多个剩余窗口和一个组合提案；模糊时段、地点、范围或例外语义无法可靠确定时不自动拆分。

## 4. 模型契约与用户证据

从 Registry 产生受控提取 Prompt 和与之对应的 Schema，定义候选列表、合法 type/slot/value、用户原话证据和意图线索。用户身份、机构、source_message_id、内部 key、memory_id、revision 均由服务端绑定或计算。

示例为目标逻辑结构：

~~~json
{
  "candidates": [{
    "memory_type": "SCHEDULE_PREFERENCE",
    "slot_code": "available_windows",
    "value": {"days": "WEEKEND", "period": "AFTERNOON"},
    "qualifiers": {},
    "intent_hint": "SUPPLEMENT",
    "evidence_quote": "周末下午也可以",
    "evidence_start": 0,
    "evidence_end": 7
  }],
  "has_unprocessed_items": false
}
~~~

偏移以 Unicode code point 为约定，实际以服务端对原文的校验结果为准；不能把示例偏移当成通用固定长度。模型输出若为空候选，任务成功结束且不建确认卡。若超过单次限额，标记未处理并分页/拆分处理，不能静默丢弃。

严格 Schema 能由模型供应商执行时传入真实 Schema；否则使用 Prompt 和 JSON 对象模式，服务端照样用 Pydantic/业务规则验证。Schema 合法仅证明结构合规，模型对否定、引用、归属和长期性的理解仍需证据校验及用户确认。

支持少量历史上下文解析“这个动作”等指代，但当前用户原话必须支持新事实；助手推荐、工具结果、RAG 和摘要不能单独构成用户证据。说“今天只有二十分钟”用于当前轮；“以后每次都二十分钟，请记住”才可提出长期提案。

## 5. 异步提取端到端流程

~~~mermaid
flowchart TD
  A[认证用户消息，持久化原文和来源序号] --> B[读取现有正式记忆并处理本轮请求]
  B --> C[最终消息、完成状态、提取 Outbox 同事务提交]
  C --> D[Worker 领取租约，读取来源并核验身份、开关与 epoch]
  D --> E[模型提取原子事实与原文证据]
  E --> F{提取结果}
  F -->|空且合法| G[任务成功结束，不创建候选卡]
  F -->|失败或超时| H[有限退避重试，最终死信告警]
  F -->|有事实| I[规范化并查询相关旧记忆]
  I --> J[程序规则比较，必要时模型辅助]
  J --> K{动作}
  K -->|重复| L[NOOP，可幂等记录独立支持来源]
  K -->|需澄清| M[创建澄清项，等待用户补充]
  K -->|新增或修改| N[保存差异提案和通知 Outbox]
  N --> O[用户确认或拒绝]
  O --> P[事务复核并应用记忆变更]
~~~

来源消息落库时绑定可信 speaker、subject、org、message_id 和受保护的范围内单调 source_seq；该序号需覆盖同一用户机构的多个会话及记忆管理命令，不能用不同会话各自的 sequence 互比。教练代学员开展业务不等于教练拥有替学员创建个人记忆的权限。

任务包含 source_message_id、source_seq、来源时的 write_epoch、提取规则版本及幂等 ID，不在消息总线复制原文。提取事件与本轮完成提交同一数据库事务；若不在同一权威数据库，必须通过额外的可靠提交协议实现，不能声称天然原子。

Worker 领取有租约并在超时后可重新领取；以主体、机构、消息 ID、策略版本和事实指纹去重。候选/澄清项、通知 Outbox 与任务终态同事务提交；空结果也记录成功，重复投递不能重复出卡。可恢复错误有限指数退避并带抖动；超过预算进死信、告警，提供受控重放。模型调用不能放在数据库锁内。

来源顺序和完成顺序可能不同：同一冲突域记录最近已生效用户表达/操作的 source_seq。旧消息晚到且与较新事实冲突时不能覆盖或生成看似最新的修改；应标记过时，必要时让用户基于当前状态重新提出。互不相关的旧事实不因无关新消息被一律丢弃。

升级提取模型或 Registry 版本不会自动重放用户历史消息。需要补提历史时必须有明确的来源范围、用户授权和重放任务，并继续执行来源水位、墓碑和当前状态校验；不能仅因为策略版本变化就绕过之前的忘记命令。

显式“请记住”应反馈“已接收，待确认”，不能在批准前说“已经记住”。明确的忘记命令独立于普通提取任务，能识别目标时立即处理；目标或范围不明确则先询问。普通完成策略不应把失败轮次误报成已成功提取。

## 6. 新旧比较与动作判定

程序先用权威主体/机构查询 ACTIVE、未过期的同 slot、关联 slot、同对象和可能重叠条件的记录；包括完整冲突域，不能只看与新 item_key 完全相同的行。先按结构化信息判断，必要时调用模型。

| 动作 | 判定与后果 |
|---|---|
| ADD | 独立对象/条件可共存；没有旧项也先生成待确认提案 |
| UPDATE | 用户明确修改同一目标；绑定 memory_id、expected_version 和前后差异 |
| REVOKE | 明确该条不再适用或用户请求遗忘；区分陈述变化与主动删除命令 |
| NOOP | 内容与条件相同；不修改正式内容版本，可按来源幂等记支持 |
| NEEDS_CLARIFICATION | 主体、指代、时间边界、范围或补充/替换不清；不能构造可直接批准的模糊变更 |

同 slot 不等于同一条；不同 slot 也可能有关联。时间/条件有交集但优先关系不明确时必须澄清，不能简单取最后一条或依赖语义相似度。模型辅助输入包括本轮原话、规范化事实、受限相关旧项及版本、允许动作；输出只能引用服务端提供的目标。自评置信度不能自动授权覆盖。

### 6.1 PostgreSQL 与可选 pgvector

基线查询完整保留结构化冲突域。可选向量索引为正式有效记忆生成版本化 embedding，补充召回可能同义的自由表达；结构化结果与向量结果合并后再做判定。向量距离不是事实真伪、肯否定或更新授权；向量未命中/失败/Top-K 截断均不能证明不存在冲突。

每条 embedding 必须关联 memory_id、memory_version、subject、org、embedding_model_version 与可用状态；检索结果回查权威表再次检查授权、ACTIVE、版本和有效期。小范围先过滤主体/机构再精确比较；共享近似索引配合过滤可能减少召回，需以精确查询作评测基准并按实测调整。[pgvector 官方过滤说明](https://github.com/pgvector/pgvector#filtering)

用户批准后由 Outbox 异步生成向量；任务落库前重查版本、状态和遗忘边界，过时任务丢弃。更新、撤销和过期使旧向量逻辑不可用并可靠清理。向量不可用时继续结构化查询；如果由此无法判定语义冲突，就澄清，不能保证所有自由表达都能自动识别。

向量是可推断的敏感派生数据，仍须权限、保留与删除规则。应用层加密正文不意味着可直接对密文做常规向量近邻搜索；必须明确数据库内可检索 embedding 的暴露面、传给 embedding 供应商的数据范围和保留策略。首期特性开关默认关闭，离线评测后再灰度。

## 7. 提案、确认与前端交互

候选以 PENDING、PENDING_CLARIFICATION、APPROVED、REJECTED、EXPIRED、STALE 表示生命周期；澄清项没有可直接批准的模糊执行内容。一次提案可包含多个 changes，前端展示操作、原文证据、旧值与新值、条件、保留的旧项、机构和期限。

提案绑定 source_message_id/source_seq、registry_version、proposal_version/hash、write_epoch、目标 ID/expected_version、ADD 预期身份及影响范围。用户批准提交 candidate_id、proposal_version 和稳定 decision_id；服务端不接受客户端替换成任意执行 payload。用户编辑后重新验证，生成新提案版本与差异，再确认。

批准/拒绝须验证当前会话身份、机构与主体、候选状态和 TTL；同一 decision_id + 相同请求返回原结果，换目标或参数拒绝。STALE 返回 409 和需要重审的原因；重新读取当前事实生成差异，不自动覆盖。组合提案全部成功或全部不提交。

候选和结果通知写入持久化聊天/通知存储并绑定 source_message_id、candidate_id、message_id 与会话 sequence。前端以 ID 去重、按序合并；迟到卡片不覆盖正在生成的后续回答，离线用户下次打开可查询。消息保留有明确策略，不能只依赖 SSE/WebSocket 的即时送达。

### 7.1 接口契约示意

路径是目标接口示意；最终可依据服务现有路由规范命名，行为保持一致。主体与允许的机构从认证上下文和服务端授权取得。

| 接口 | 输入与结果 |
|---|---|
| `GET /v1/memories` | 查询本人授权范围，支持类别、slot、状态和分页；返回版本、条件、来源可用状态 |
| `GET /v1/memory-proposals` | 查询候选、差异、状态与有效期；不会把候选视为正式记忆 |
| `POST /v1/memory-proposals/{id}/decision` | 提交 approve/reject、proposal_version、decision_id；返回已应用结果或原幂等结果 |
| `POST /v1/memories/{id}/correct` | 用户明确编辑并确认，提交 expected_version、受控值和 operation_id |
| `POST /v1/memories/{id}/revoke` | 用户明确指定目标撤销，提交 expected_version 和 operation_id |
| `POST /v1/memories/clear` | 明确范围的清空命令，返回 operation_id 和逻辑生效/清理状态 |
| `GET /v1/memory-operations/{operation_id}` | 查询自己的幂等命令结果与异步清理状态 |
| `PATCH /v1/memory-settings` | 分别管理提取和个性化使用开关，服务端校验范围和并发版本 |

输入错误返回明确的参数错误；未认证/未授权按服务统一约定处理且不泄露他人数据；已过期候选返回可区分的过期状态；目标或提案变化返回 409 及可重新审阅的状态。暂时不可用和限流响应不冒充成功；自动重试只针对安全且带原幂等 ID 的命令。物理删除若异步执行，返回可查询的任务状态，不把已接收等同全部副本已清理。

## 8. 权威数据与存储结构

| 表/设施 | 关键字段与职责 |
|---|---|
| chat_messages | 已认证的用户原话、角色、主体、机构、会话顺序、范围 source_seq、加密正文、保存/删除状态 |
| memory_profiles | `(subject, org)` 主键；revision、write_epoch、范围事件序号、提取/使用开关、删除水位 |
| memories | id、subject/org、type/slot/scope/item、加密 payload、HMAC、status、version、schema_version、valid_from/expires_at、source、确认/复核和保留字段 |
| memory_proposals | id、来源、加密 changes、状态、hash/version、TTL、epoch、目标版本及决策 ID |
| memory_events | operation/event_index、动作、actor、目标与旧新版本、结果引用和审计时间，不默认复制正文 |
| memory_tombstones | 被撤销对象/范围的规范身份或保守删除范围、来源序号水位与保留策略，阻止旧事件复活 |
| memory_supports | memory_id/version、source_message_id、source_seq、证据定位和确认事件，独立来源去重 |

| outbox / jobs | 事件、lease、尝试次数、重试时间、死信与消费去重 |

## 9. 唯一约束与命令事务

同一主体、机构、slot、scope、item 上允许一条 ACTIVE 且未脱敏记录。可用静态部分唯一索引实施；只有完全相同身份受该索引保护，相关 slot 和时间重叠还要服务层验证。索引谓词不能包含 `expires_at > now()` 等依赖当前时间的表达式；读取按时间校验，写入同一身份前在事务中先处理已经到期的 ACTIVE 项。[PostgreSQL CREATE INDEX](https://www.postgresql.org/docs/current/sql-createindex.html)

首期采用用户机构 profile 行作为统一短事务锁，所有批准、管理编辑、撤销、到期状态变更和清空遵循同一协议。若 profile 尚不存在，先安全创建再加锁；涉及多个 profile 时按固定顺序获取。写入在 profile 锁后重新读取相关目标与冲突域；锁内不进行模型、HTTP 或等待用户。

批准事务顺序：

1. 检查用户/机构/目标授权，校验 operation ID 与请求摘要；相同幂等请求返回原结果，不同请求拒绝。
2. 锁定 profile 与候选，验证 PENDING、TTL、proposal hash/version、write_epoch、来源序号及删除水位。
3. 按固定顺序锁目标 memory；重查目标 expected_version、ADD 身份空缺和完整冲突域。
4. 检查 source_seq 未被同冲突域中更新的已生效用户决定取代。无关的 revision 变化不会自动令所有候选失败。
5. 执行全部变化，更新记忆与候选终态、审计、revision、必要 tombstone，写入通知/向量 Outbox；整体提交。
6. 提交后通知前端并异步清理。客户端响应丢失用相同 decision_id 重试，返回已保存的结果。

在相同版本上并发修改时，只允许一方成功；另一方 STALE 后展示当前差异重审。并发新增同身份受唯一约束保护，不同但重叠的范围依靠所有写入口共享 profile 锁和重新检查。若未来改为更细粒度锁或 SERIALIZABLE，必须证明跨范围冲突仍被串行化，并对可恢复事务冲突有限重试；不能只做锁外的一次查询。[PostgreSQL 事务隔离](https://www.postgresql.org/docs/current/transaction-iso.html)

不跨数据库宣称原子提交：权威 Memory、候选、事件、Outbox 和需要作为提交屏障的最终结果应位于同一事务边界；其他存储通过版本化发布和消费可靠同步。

## 10. 读取与 Prompt 注入

~~~mermaid
flowchart TD
  A[当前请求与可信身份] --> B[确定 actor、subject、机构与用途]
  B --> C[校验用户或教练授权]
  C --> D[读取权威 revision 与用途白名单]
  D --> E[读取 ACTIVE，检查生效期、条件与复核]
  E --> F[本轮明确输入、关键约束、相关性和预算]
  F --> G[构造 MemoryContextPacket 与注入版本清单]
  G --> H[固定 system、Memory 数据上下文、当前消息]
  H --> I[模型生成，程序验证结构和可验证约束]
  I --> J[版本/到期提交屏障，保存结果与使用 Outbox]
  J --> K[前端展示和刷新恢复]
~~~

| 用途 | 读取策略 |
|---|---|
| 本人训练计划 | 相关目标、偏好、器械、可用/偏爱时间、时长；必要条件不确定则询问 |
| 普通聊天 | 自动选择沟通偏好和当前问题相关条目 |
| 健身问答 | 沟通偏好与本问题必要的训练上下文 |
| 预约 | 时间偏好只作为建议；业务可约性、合同、授权实时查询 |
| 客服 | 沟通偏好及本问题确有必要且有权限的条件 |
| 文档生成 | 相关格式、沟通偏好和必要主题上下文；私人记忆不自动公开 |
| 教练代学员 | 先验证授权，再读取学员训练相关白名单；学员沟通偏好默认不外传 |
| 用户查询记忆 | 本人机构范围分页展示记忆、状态、条件、来源与管理入口 |

system 放稳定角色、权限和输出规则。Memory 放独立的结构化数据上下文；只有实际调用工具才产生配对的 tool call/result。拒绝把 Memory 正文中的指令升级为系统指令。训练计划严格字段与必要安全/业务条件不能因为“简洁”偏好省略。

用户本轮明确输入优先于适用的旧偏好；旧事实冲突、关键约束未知或已到复核期时澄清。能程序校验的器械范围、时长等约束由校验器验证，不把“喜欢某动作”擅自提升为硬约束。读取失败与用户没有记忆是不同状态：普通回答可降级；必须依赖约束的训练计划应询问或暂停，不猜测。

运行时装配正文，记录注入的 memory_id/version、profile revision 与最早到期时间；Checkpoint 以引用及执行进度为主。缓存必须带主体、机构、用途与 revision，命中后仍检查最早 expires_at；不能只靠后台过期 Worker 或 TTL。

## 11. 支持证据、引用和计数

| 字段 | 意义与更新来源 |
|---|---|
| support_count | 同一版本有多少独立来源消息明确支持；同一消息重复消费只计一次 |
| last_user_asserted_at | 用户最近明确表达的来源时间，不用 Worker 时间冒充 |
| last_confirmed_at | 用户最近明确批准/复核当前版本的时间 |
| injected_count | 被实际注入模型请求的观测，可暂保留在指标中 |
| referenced_count、last_referenced_at | 已持久化最终结果声明关联且通过引用范围验证的次数/时间 |
| applied_count、last_applied_at | 程序能验证其被用于约束校验的次数/时间 |

用户原文证据、RAG 知识 citation、Memory 使用关联是不同关系。支持不等于确认；注入不等于引用；引用范围合法不证明模型内部因果使用；高引用不等于更真实。普通沟通偏好可能不在正文标注引用，不可因引用为零就断定无用。

目标生成结构允许返回 `used_memory_refs`（memory_id/version），与知识 evidence_ids 分开。服务端只接受本次授权、确实注入且仍合法的版本；本轮已覆盖的旧条件不能当作有效采用。确定性校验器可另记录 APPLIED。

最终结果与使用事件在同一权威事务提交；同一稳定输出/计划版本、同一记忆版本和使用种类唯一。一次计划多处关联同一记忆默认一次；重试、流式分片、重复消费和刷新不重复计数。晚到事件仍属于旧 memory_version；时间聚合取 MAX。失败、取消、未提交的临时输出不算成功关联；已持久化但推送丢失的结果可恢复，算已提交，不代表用户已阅读。统计写独立表，不递增正式内容 version。

## 12. 生命周期、过期与遗忘

正式状态：ACTIVE → REVOKED 或 EXPIRED；纠正产生新的内容版本。`next_review_at`、`retrieval_tier=NORMAL/COLD`、`user_pinned` 是独立策略，不等同正式状态。

| 场景 | 执行策略 |
|---|---|
| 用户明确的有效期到期 | 读取立即排除；后台扫描标记 EXPIRED、更新 revision、审计、向量和通知 |
| 偏好可变但未设到期 | 按 slot、用途和最后确认时间决定是否需要复核；不自行当成已失效 |
| 长时间未引用 | 低风险、非关键条目可降低排序或 COLD；管理页/明确查询可找到并恢复 |
| 用户固定保留、关键约束 | 不因低频自动移除；仍遵守明确到期与用户撤销 |
| 用户撤销单条 | 立即 REVOKED、版本和 revision 增加，写审计/Outbox，建立目标及必要范围墓碑 |
| 用户清空 | 在事务内更新 write_epoch、revision、来源水位并使待处理候选失效；后台处理正文与派生清理 |
| 用户要求删除 | 按明确的删除范围执行 Memory、候选、事件/证据、向量、缓存及关联档案的约定；备份按保留与恢复策略处理 |

有效时间读取按权威时间检查，即使 Worker 延迟也不能使用过期项。引用次数和最近引用时间只作有限排序/冷却信号，不刷新 last_confirmed_at 或 expires_at；阈值按 slot 配置并通过评测决定。COLD 不是删除；复核不等于已过期。不能用模型近期频繁复述或用户长期不活跃作为事实真实性证明。

单条撤销的墓碑含受影响规范身份及 source_seq 边界；迟到的旧来源任务不得恢复同一条。若语义归一或删除范围不确定，保守阻止旧来源重新生效并要求新授权。清空通过全范围 write_epoch 和源消息水位阻止旧 Outbox、候选批准和 embedding 作业复活；任务必须持有来源时的 epoch，不能在处理时重新读取最新 epoch 冒充新任务。撤销之后用户新的明确表达可再次发起并确认。

## 13. 撤销后缓存、摘要、Checkpoint 和在途运行

撤销事务写 REVOKED/version、revision、墓碑和 Outbox；提交后逻辑停止使用，缓存/摘要/向量物理清理由幂等 Worker 重试。权威 revision 和记忆状态不可用时不能复用未知是否过期的个性化缓存。

摘要和模型上下文记录可能传播的注入依赖，合并摘要时继承来源依赖，不能只依赖模型自报引用。会话中涉及多个主体时分别记录 profile revision；教练会话使用学员记忆后，学员撤销也能使该派生上下文失效。旧摘要整份失效或从已经过滤的来源重建；无法可靠清除时切换到新模型上下文基线。

Checkpoint 的模型消息与业务执行状态分开：保留待确认 ID、工具结果、流程进度与幂等标识；失效或重建旧模型消息，不直接删除整个业务中断点。历史 assistant、user、tool 文本可能含旧事实；不可靠时不再原样发送。必须维持 tool call/result 配对，不为重建上下文重放 Java 写操作。

在途运行在模型请求前校验依赖，撤销时通知取消或重建。最终回答、摘要、使用事件和权威上下文发布时，在同一权威事务/提交屏障中再次验证 revision 与有效期；使用旧修订号的结果不得成为新提交结果。不同数据库中的 Checkpoint 物理写可能延迟，读取和发布仍以权威屏障拒绝过期状态。

例如 A 基于 revision 12 生成摘要，撤销后为 13，A 即使发现摘要表已空，也不能重新发布旧摘要。SSE 已发送的片段和已经发送给模型供应商的内容无法撤回；后续片段按 run/版本停止或丢弃。已经提交的 Java 业务操作不因 Memory 撤销而自动回滚或重放。

用户查看历史消息与模型可用上下文是两回事：忘记 Memory 不自动删除历史聊天；历史若保留，旧消息需要从自动输入中屏蔽或使用新基线。用户要求删除聊天时执行单独删除范围；新一次明确表达可用于本轮，但跨会话重新保存仍需新确认。

## 14. 故障策略、授权与隐私

| 故障或情况 | 策略 |
|---|---|
| 模型提取超时/格式非法 | 有限重试、死信和告警；不伪造空成功，也不写正式 Memory |
| 合法结果为空 | 任务成功完成，无候选卡 |
| 用户拒绝或候选过期 | 候选终态留审计，不改变正式条目 |
| 决定响应丢失 | 原 decision_id 查询或重试，返回原结果 |
| 提案版本变化/目标变更 | STALE/409，展示最新差异，重新确认 |
| Outbox 重复或消费者崩溃 | 至少一次投递；消费者依靠稳定 ID 幂等提交 |
| embedding 生成失败 | 结构化基线继续工作；未知的语义冲突澄清 |
| 撤销后清理失败 | 权威读/提交屏障仍阻止复用；重试、对账和告警 |
| 读取记忆失败 | 区分服务不可用与无记忆；必要条件不能猜测 |
| 通知离线或重复 | 持久化查询与 ID 去重；网络推送仅负责加速 |

所有读写在服务端确定 actor、subject 和组织。教练代读必须经过可信授权与用途白名单；不接受模型或客户端提供任意 subject 作为授权。普通候选只从被认证用户对自身的明确表达提取，代他人保存需单独授权方案。

跨 Java 网关与 PostgreSQL 的授权变化不能假装属于同一数据库事务。常规代读在每次请求开始时验证并使用有明确期限/版本的授权凭据；必要的最终发布检查需要再次验证。若产品要求撤权后的强实时阻断，需要将权威授权版本安全同步到同一提交屏障，或采用有明确撤权传播时限的授权租约，并将该时限写入产品和运维契约；外部授权检查本身不会与本地事务天然原子。

保留期限、密钥轮换、第三方模型/embedding 的数据处理、访问控制、备份恢复与删除时限需形成可配置的运维策略；审计记录保留最小必要元数据。应用层加密正文、向量和已发出的外部请求具有不同清理能力，不能承诺已经展示/发送的内容被追溯收回。

上线前必须为聊天、候选正文、正式条目、支持记录、使用事件、死信及备份分别配置保存期、删除行为和恢复对账策略。首期候选 24 小时只是提案有效期，不等于其终态审计或所有聊天自动在 24 小时删除。若用户单独删除来源聊天而保留正式记忆，页面应说明来源原文已不可用；不能把已删原文假装仍可查阅，或自动以历史缓存恢复。

## 15. 验收、监控和上线

在项目真实样本上分别评估：提取准确率/召回率、拒绝不应提取内容、同义归一、否定及时间关系、ADD/UPDATE/REVOKE/澄清准确性、作用域隔离、向量相对结构查询的增益、最终计划约束正确率。批准率只能作为体验指标，不能代替事实准确率；线上延迟、成本与 SLO 由负载测试和产品要求确定。

必要验收至少包括：

1. 空候选成功、模型失败重试、超过限额继续处理、同一消息重复消费。
2. 助手建议/他人引述/一次预约不形成用户记忆；本轮临时要求不改长期记录。
3. 周末上午加下午、明确替换、范围不清、局部重叠、时区未知和夏令时边界。
4. 同义重复、不同对象共存、喜欢与不喜欢、同 slot 不同条目、关联 slot 冲突。
5. 两个审批并发修改同版本、范围重叠并发 ADD、响应丢失重试、同决策 ID 不同 payload 拒绝。
6. 迟到旧消息不覆盖新决定；单条撤销/全量清空后旧任务、旧候选和旧 embedding 不能复活；新明确表达可再次确认。
7. 读取即检查过期；清扫延迟不使用已过期记忆；频繁引用不能自动续期。
8. 撤销和在途生成/摘要发布竞态；旧版本不能发布；工具配对及待确认业务仍可恢复且不重放。
9. 同一用户不同机构、不同用户、教练代学员授权/撤权、缓存与向量无越权。
10. 向量缺失、落后和 ANN 过滤低召回；结构化冲突检查仍有效。
11. 同结果多处引用、重复事件及旧版本迟到仅按定义统计；沟通偏好不因零引用自动删除。
12. SSE 丢失、用户继续对话后迟到卡片、刷新恢复、通知 ID 去重与顺序。
13. 删除范围、摘要/缓存清理失败重试、备份恢复后删除边界持续生效。

监控候选生成/批准/拒绝/编辑、空结果/提取错误、语义误合并与误覆盖、版本冲突、过期/撤销后违规复用、向量召回、清理延迟、死信和 Outbox 积压；日志脱敏。异常情况下可分别关闭自动提取、向量召回和个性化读取。

上线顺序：先确认 Registry、消息持久化与权威事务边界；实现可靠命令/并发和生命周期；再实现公共异步提取；接入 ContextBuilder、通知和引用统计；完成失效与权限测试；影子评测后小流量启用、观察和回滚。向量待真实评测通过后独立灰度。任何迁移仅确定性归一可信旧数据；模糊旧值需用户复核，未留快照的已覆盖内容不承诺恢复。

## 16. 面试表达

“我设计的 Memory 以 PostgreSQL 为权威存储，将用户明确表达抽取为候选，在受控维度下与相关旧记忆比较，区分新增、重复、修改、撤销和澄清。同一类型允许多个条目；异步提取通过 Outbox 和幂等 Worker 保证可恢复。用户确认时按版本和完整冲突范围再次检查，并把正式记忆、候选、审计和通知原子提交。读取按用户、机构、授权、用途和有效期选择；向量仅做可选语义召回。用户证据和模型使用分别统计，过期/撤销通过修订号、删除边界和发布屏障失效缓存、摘要和旧任务，保留独立业务流程状态。”

文中是设计和验收目标；介绍项目时应据实际落地情况区分已经实现与计划实现。
